# ReportEngines — decisions

> A durable artifact of **decisions**, not documentation. Intent lives here; `.cs` is its compile target.
> Platform-wide goal and working method: [/CLAUDE.md](../CLAUDE.md).
> What a blank declares and how its data is fetched is decided on the other side of the seam — [Print forms](../Platform/A2v10.Metadata/CLAUDE.md#print-forms-paper-under-one-act); this layer receives a model and never parses the layout to learn what to ask for.

## Loading a blank: the first byte says the format, the route only says where the bytes are

A blank arrives by one of three routes — a file named in `model.json`, a text resolved from the model (`{{Model.Field}}`), a stream handed in by the metadata print layer. One rule: **the format is decided by the first significant byte — `<` is XAML, `{` is JSON — in one recognizer, `TemplateReader.ReadReport`, the same for all three.** Pinned by `Test.PdfReportEngine` (Template Format). Decided 2026-09.

- **One discriminator, because the second case cannot exist.** XAML's root element already says whether it is a `Page` or a `Spreadsheet`; JSON is always a workbook — `Page`'s layout (`Columns`, `Header`, `Footer`) is `[JsonIgnore]`, so a page cannot round-trip through JSON at all. What was missing was never "the kind", only "the format on that route": JSON from a file, XAML from the database or a stream.
- **The extension names candidates, not the parser.** The file route probes `.vxaml`, `.xaml`, `.json` and hands whatever it found to the same recognizer. Dispatching by extension was refused: it puts an extension into the report name in `model.json`, and then `f` and `f.json` are two spellings of one name — the pair the print layer already refuses in `FileOf` — and two mechanisms answering one question drift. Price kept: with both `f.vxaml` and `f.json` on disk the probe order wins silently, which is a property of probing and is unchanged.
- **Styles are applied at the parse, not at the call site.** That is where the routes had already drifted — XAML got `ApplyStyles` inside the reader, JSON got it in the engine, twice, with the same arguments by luck rather than by rule.
- **The BOM is dropped by the recognizer, and only there.** `XmlReader` throws on it in position 1 and `JsonSerializer` on `U+FEFF` in a string, so it must go before either is called — and only the recognizer knows it was there. Same shape as the image signature check next door; deliberately the same shape, so neither reads as special.
- **The candidate list is one list, in `A2v10.Infrastructure`.** Two assemblies open a blank — the engine to draw it, the metadata layer to read the `Model` section out of the same file — and two copies of `[".vxaml", ".xaml", ".json"]` drift silently: the blank is found for one reader and missing for the other. `ReportTemplateFile.Open` is that one probe; `PrintRequest.FileOf` now composes a path without an extension.
- **A blank carries its fetch declaration in `<Page.Model>`, and that slot is on `Page`.** Both roots are pages — `Spreadsheet : Page` — so one property serves a page blank and a workbook blank, and no interface is needed to say who can declare a fetch; `Workbook` is not a root and never carried it. The text inside is the same JSON the JSON blank holds under its top-level `"Model"` key: a XAML-native grammar for that tree would be a second grammar for one thing, and the metadata layer, which does not reference `A2v10.Xaml.Report`, would read it as XML either way. **`Model` must stay `[JsonIgnore]`**: in a JSON blank `"Model"` is an object, and binding it into a `String` would break every print blank in existence — pinned, not left to memory.
- **`ExcelReportEngine` was left alone.** It still reads JSON from the model and is otherwise unimplemented.

## Report expressions: a path, or JS with one scope

What a cell or a binding says is evaluated against a **scope** — the model at the top, the element of the collection inside a range. One rule: **a path is read from the data — from the current scope, or from `Root`/`this` at its head; everything else is ordinary JS, where `this` IS the scope, free names come from the root, and `Root` is the explicit root from any depth.** Pinned by `Test.PdfReportEngine` (cases over the rule and over the workbook's row walk), not by the look of a rendered page. Decided 2026-09.

- **`this` is bound as a receiver, never substituted into the text.** The old wrapper was an arrow, whose `this` is lexical and takes no receiver, so the author's `this` had to be rewritten — mangling `thisYear` and `'this'` inside literals, and only when the expression happened to contain `(`. Price, paid knowingly: a receiver stops at the wrapper, and the author's own functions are usually arrows, so the scope reaches them as an argument — `{rowTotal(this)}`, not `{rowTotal()}`. Banning arrows was refused: composition (`rows.map(rowTotal)`) would then need `.call`, and enforcing it means parsing the author's JS, which this layer refuses to do everywhere else. `{fn.call(this)}` stays expressible for whoever prefers the `template.ts` manner.
- **Scope is a parameter of `Compose`, never ambient.** No scope stack: composers hand closures to QuestPDF, and the moment of invocation belongs to the library — a mispaired push/pop is silently wrong, the one failure mode this layer cannot see. The parameter already existed and carried three meanings (row, collection to iterate, computed cell value); it now carries one, which is what deleted both composer caches and the walk pre-computing a nested element's `ItemsSource`. A parent link is not built: the two things an expression can want are `this` and `Root`; if a third is ever wanted it is `$parent`, and it belongs in the object handed to JS, not in the data — an `ExpandoObject` has no hidden property, so a link there is a cycle every walker meets.
- **The shape of the text picks the branch, not a marker — in one place.** `RenderContext.Evaluate` is the only entry: cells, `Bind` on a page, `If`, `ItemsSource`, images. A path (names joined by dots, an index allowed on a name) is walked in C#; everything else is JS. A path never enters JS, because there `Decimal` becomes `Double` and `Byte[]` an array of numbers. `{a.b:format}` is the cell's syntax, so `Resolve` peels the format and asks the same entry. Refused: a marker — outer parens, and then "a paren anywhere". Both send every paren-less expression (`Price * Qty`, a ternary, `Root.X`) to the walk, which returns `null` without an error, and making that loud needs the path grammar anyway. The outer-parens marker had already cost an hour on the first real form (`{spellMoney(Document.Sum)}`). `Root` and `this` are two words the walk starts from, not exceptions sending a path to JS; so the wrapper no longer prefixes `this.`, and Page and Workbook no longer read differently (`Bind` used to go to JS always).
- **Prices of that split.** What exists only in JS must be written as an expression: `{Rows.length}` and `{Bind Rows.length}` are empty, `{(Rows.length)}` is 2. A missed path is silently empty wherever it is written, including `this.X` and `Bind`, which used to throw `TypeError` there — and so is `Agent.Name` when `Agent` is null, which is right for paper. A number coming back from JS is a `Double`, so type guessing by CLR type yields Number where the path yields Currency — declare `DataType` and the guessing is not consulted.
- **Nesting falls out for PDF; the workbook still caps at two.** `ItemsSource` is evaluated in the received scope, so a nested table computes its own collection at any depth without the parent preparing it. The workbook flattens rows into a matrix with two hand-written loops, so a third range has nowhere to go — the walk, not the scope.
- **The box has a budget: recursion depth, a statement count, a timeout.** An expression has no authority — no `AllowClr`, it sees the model and four functions — so what it can still take is resources: unbounded recursion is a `StackOverflowException`, which cannot be caught and kills the process; `while(true)` hangs a request thread. The counter is deterministic and does the work, the timer is a backstop for what it cannot see (a heavy native call). Counted per call, not per document — pinned by `ScriptBudget`, so a thousand cells never add up to one overflow. Sized for a `reduce` over tens of thousands of rows, not for what a template reasonably needs.
- **Expressiveness is not restricted; the answer to cryptic code is the loop, not a ban.** Template literals (`` {Bind `…${x}…`} ``) and anything else JS accepts stay: a ban is unenforceable without parsing the author's JS, which this layer refuses everywhere. What keeps it safe is the budget above and, when it is built, a check that runs a template over data and reports what threw, what came back `undefined` and which numbers lost `Currency` — not yet built, and owed before an LLM writes blanks unattended.

## Report images: one value, one resolver

A file named from inside a blank is read by `IAppCodeProvider`, from the report's folder. One rule for what such a slot holds: **the value is either bytes or a file name, and raster-or-SVG is decided by the first bytes, never by the extension.** Pinned by `Test.PdfReportEngine`. Decided 2026-09.

- **The base is `reportInfo.Path` on all three routes.** `_templatePath` was a path in the provider's terms used as a filesystem path, and it was empty on the stream and database routes — so `File.ReadAllBytes` searched from the process working directory. A file named inside a blank sits beside the blank whether the blank came from a file, a stream or a row; the folder is the one thing all three already carry.
- **`FileStreamResource`, never `FileStreamRO`.** Under the CLR provider these are different channels: RO returns `Encoding.UTF8.GetBytes(GetText(path))` — text only, so a raster comes back as garbage and says nothing. Under the file provider both are the same file, so file deployments do not move, and in CLR images in reports work for the first time. Choosing the channel by extension was refused for the same reason: the silent half is the text one.
- **`FileStreamRO` stays nullable; `FileStreamResource` stopped being.** They are asked different questions: RO is probed — "is there such a file" (`.vxaml`, then `.xaml`) — so `null` is a real answer; `Resource` was probed by nobody, all three call sites treated `null` as fatal and each invented its own message. Absence is now the provider's own throw, and the three `??` arms are deleted. It has to be the provider's, because only it knows WHAT it looked for: MSBuild replaces invalid characters in FOLDER names with `_` and the CLR provider does not, so the computed resource name is the one debuggable fact and it cannot be named from outside. Price: `Stream?` → `Stream` on a platform interface, and `DataService` lost the word "Template" from its message. Half of this — a throw in the CLR provider alone — was refused after being written: it makes the contract depend on the deployment, live on files and dead on CLR.
- **Paths are not the report layer's business.** Subfolders and `..` are normalized by `MakePath`, refusals (rooted, escaping the app) are its concern. A fact for later, not a hole opened here: today `MakePath` has no such refusals.
- **The signature decides, and the BOM is dropped with it.** Skip BOM and blanks, `<svg` or `<?xml` → SVG text, otherwise bytes; png against jpeg is the decoder's problem. Side effect worth the branch: an SVG living in `varbinary` starts drawing — until now it was silently empty. The BOM leaves the text because it breaks the SVG parse, and only the recognizer knows it was there.
- **Only where a picture is expected.** Image and Watermark resolve; a workbook cell keeps a String as text, or every text cell becomes a file name. The type says so — `ReportImage` is `Raster` or `Svg`, so a slot cannot be both or neither, and drawing is the only place the difference is still visible.
- **`Source` and `FileName` are one slot with two spellings.** Bytes and a name are the same question after the resolver, so the composer asks once and the two names stop meaning two mechanisms. Kept both: old blanks spell `FileName`, and deleting an attribute buys nothing here.
- **Bytes never pass through JS.** A bound slot asks the one entry, `Evaluate`, and a path there never reaches Jint, which hands a `Byte[]` back as an array of numbers and loses the picture silently. That deleted `GetValueAsByteArray`, which reached the value by splitting the expression at its last dot and could only ever read one level.

The watermark is the second slot, and it is where the geometry decision sits.

- **`Watermark` on `Page`, composed in `ReportDocument.Compose`.** One place because both branches pass through it and `_page` is in hand there; written in `PageComposer` and `SpeadsheetComposer` it would be two places to drift.
- **`Background()`, not `Foreground()`** — the mark goes UNDER the content. Accepted price: a cell with an explicit fill covers it (`DecorationStyles` paints a solid color), which is fixed on the blank's side, not in the platform.
- **Geometry lives inside the SVG.** Rotation, opacity and size are the file's, so no `WatermarkOpacity`, no angle, no size property — QuestPDF has `Rotate` but no `Opacity` on a container, so half of such a set could not be honoured anyway.
