# Анализ пакета A2v10.Metadata — 2026-09-26

Чтение всего пакета целиком (≈16.7k строк, ~100 файлов): дефекты, протечки абстракций, мёртвый
код, и поверх них три оценки — подхода, пригодности для ERP на метаданных, производительности
сгенерированного SQL. Каждая находка названа строкой и сверена grep'ом по репозиторию без
`Obsolete/`; что уже стоит в [ISSUES.md](ISSUES.md), сюда не попало. Номера строк на 2026-09-26.

Метод: четыре независимых прохода по областям (Database; Meta + Provider; Form/Xaml/Script/Generator;
Builders/Reports/остальное), каждая находка перепроверена чтением названной строки. Что не
подтвердилось, не записано.

## 1. Дефекты

Ведут к поломке на достижимом входе, по убыванию цены. Чиним по одному; закрытое помечается
датой, не удаляется.

### 1.1. `Show` на индексе справочника открывает action, которого нет

`CommandXaml.cs:62-64` кладёт `EntityCommandType.Show` в стандартный бар каждого каталога, `:167`
ведёт на `{Endpoint.Path}/show`. `BaseModelBuilder.cs:71` грузит под `show` модель карточки, но
`CreateTemplateAsync` (`:81-95`) и `CreateXamlContainer` (`IndexPageXaml.cs:379-393`) арма `show` не
имеют: клик даёт `NotImplementedException`. Валидатор этого не видит: он идёт по baked forms, а
`show` не форма. todo.txt 27 («Element.Show Endpoint») это и есть.

### 1.2. Шаблон карточки: не-документ без `computed`/`total`/`inherit`, документ без `unique`

`EditTemplate.cs:46-66` (generic) выпускает только required и unique; `:141-183` (document)
выпускает computed/total/inherit и не выпускает unique. Бейк ни одно правило по виду не отказывает
(`DeclarationBake.cs:86-95`, `:226-233` проверяют только имена), `.d.ts` объявляет computed для всех
видов (`EditTSMap.cs:80`), fetch шлёт `?inherit=` для всех (`ControlsXaml.cs:31-37`). Справочник с
`computed` на строках: тип обещает член, геттера нет, молча. Документ с `"unique": true` на
номере: клиентской проверки нет, дубль ловится только save'ом.

### 1.3. FK на `Document` журнала прибит к одной таблице

`CliDatabaseCreator.cs:149-150`: для любой `IsRef`, включая `ColumnType.Document`, FK на
`RefTableCheck.Storage`. `PostStatements.cs:109-111` объясняет, зачем `DocumentType`: «Ids are per
table, so two documents declaring 'table' both have a row 5». Журнал с `Document` + `DocumentType`
и второй документ со своим `table`, проводящий в него: insert (`:267-271`) пишет id второй таблицы
в колонку с FK на первую. Падает громко, на проводке; но падает ровно тот случай, ради которого
дискриминатор заведён.

**Закрыто 2026-09-26:** `not in (N'jrn', N'led')`, мёртвый `rep` снят; комментарий в процедуре

### 1.7. `unique` на колонке не даёт индекса в БД и типизирован bigint

**Половина закрыта 2026-09-26:** `@Id` в `SqlBuilderUnique` идёт `AddTyped(PlatformId.SqlDbType)`, как
везде. Индекса по-прежнему нет.

Индексы пишутся только из `TableMetadata.Indexes` (код, `CliDatabaseCreator.cs:172-187`);
`TableColumn.Unique` читает один `EditTemplate.cs:49-78`, клиентский `$asyncValid`. Две
параллельные записи с одним кодом проходят обе. ISSUES 3.9 исходит из того, что индекс есть
(«индекс был подстраховкой блокировки»). Вдобавок `SqlBuilderUnique.cs:35` `AddBigInt("@Id", ...)`,
тогда как все остальные `@Id` слоя идут `AddTyped("@Id", PlatformId.SqlDbType, ...)`
(`SqlBuilderPost.cs:91`, `SqlBuilderDbRemove.cs:73`, `SqlBuilderTree.cs:221`): на базе с
`uniqueidentifier` `t.Id <> @Id` даёт operand type clash.

### ~~1.8. Единственная небрэкетированная колонка в генераторе~~

**Закрыто 2026-09-26:** `a.[{orderColumn.Name}]`.

`SqlBuilderIndex.cs:97` `field = $"a.{orderColumn.Name}"` рядом с `:91` `[{...Presentation}]` и
`:194` `a.[{x.Name}]`. Колонка `Key`, `Group`, `Plan`, `Desc` проходит `CheckNames` (буквы), сортировка

**Закрыто 2026-09-26:** `TransName` через `KebabToPascal`; других `ToPascalCase` по сегменту пути в

`[Stock-moves!TStock-moves!Array]` и значение таба с дефисом.

**Закрыто 2026-09-26:** `AllColumns()` во всех трёх местах, где резолвится `inherit`: бейк
(`field`, `ref`), `RefMapBuilder.SourceColumn` (источник в целевой таблице), `SqlBuilderFetch.FetchColumns`

`DeclarationBake.cs:43` `var columns = table.Columns;` против `:28` `AllColumns()` и комментария

### 1.11. `metadata.json` в модуле роняет обход деплоя

`DatabaseMetadataProvider.cs:1443` `IsBuildOutput` пропускает сегменты на `$`, то есть пути
`$module/...` здесь ожидаются (`AppCodeProvider.cs:123-124` их так и даёт). `:1455` отдаёт тот же
трёхсегментный путь в `ParsePath`, который на нём бросает (`:1190`). Один `metadata.json` в
модуле вне bin/obj валит `AllElementsMetadata` целиком.

## 2. Протечки: одно понятие в двух местах

- **Тип колонки → контрол написан дважды.** Строка `ControlsXaml.cs:76-141` против карточки
  `:508-660`: в строке `Bit/Boolean` уходит в `_ => TextBox`, `Memo` однострочный,
  `Document`/`Folder` TextBox над ссылкой; в карточке `:641` CheckBox, `:532` Multiline, `:577/:585`
  Selector. Строка с `boolean` редактирует bit текстом.
- **«Мера ли это» отвечается в семи местах, и списки разные.** `XamlExtensions.cs:31-32`
  (`ToXamlDataType`: `Integer`, `Number`, `Percent`, `Factor` → String), `:43-44` (`ToXamlAlign`,
  шесть типов), `:58-59` (`ToXamlColumnRole`, пять, без `Qty`), `:68-75` (`BindSheetCell`, `Factor`
  вправо только здесь), `ControlsXaml.cs:646-647` (карточка: только Money/Float/Decimal, Amount/Price/Qty
  влево), `DefaultFormBuilder.cs:130`, `PostStatements.cs:193` (ISSUES 6.1). `JsExtensions.cs:24`
  типизирует `int` как `number`, так что `Integer` в `.d.ts` число, в XAML String. Ответ один, рядом
  с типом.
  **Одно место из семи снято 2026-09-26:** `PostStatements` спрашивает `TableColumn.IsAdditive` (ISSUES
  6.1, CLAUDE.md «Storno»). Это другой вопрос — «складывается ли», а не «число ли», — так что
  остальные шесть он не заменяет.
- **Колонки литералом там, где рядом константа и тип.** `rv`: `DataTableBuilder.cs:113`,
  `SqlBuilderPlain.cs:354` против `ColumnType.RowVersion` на `:349` и `FieldNames.RowVersion`.
  `Void`/`Done`: `SqlBuilderIndex.cs:132`, `SqlBuilderFetch.cs:121,137`, `SqlBuilderOperations.cs:36,58`,
  `SqlBuilderDbRemove.cs:55-66`, `SqlBuilderPlain.cs:316`; константы в `SqlBuilder.cs:109`,
  `SqlBuilderPost.cs:41-43`, `SqlBuilderTree.cs:43`.
- **Один закон, две реализации.** Правило идентификатора: `DatabaseMetadataProvider.cs:383` и
  `:867-868`, два текста сообщения (`:386`, `:852`). `MergeByKey` `:1001-1009` байт в байт `ByKey`
  `DeclarationMetadata.cs:55-63`, под комментарием `:1011-1013` про дрейф. `StateDefaultColumns`
  `TableDefaultColumns.cs:148-156` копия `EnumDefaultColumns` `:121-132`, «word for word» ничем не
  скреплено. Формат ключа кеша трижды: `EndpointLoad.cs:25`, `DatabaseMetadataCache.cs:123`, `:133`.
  Формат адреса дважды: `EndpointMetadata.cs:39`, `TableMetadata.cs:686`, с комментарием «has to be
  comparable to an address».
- **Отчёты.** `LedgerReportBuilder.cs:41-91` и `TurnoverReportBuilder.cs:20-60,81-84,112-116`
  скопированы (параметры, фильтры, период, `[Filter!TFilter!Object]`), отличаются одной `;`

## 5. Оценка подхода

**Что держится.** Ставка «shape → всё производное, один канал IDataModel, ничего не генерится в
.cs» держится. Загрузка как beam действительно ловит: большинство отказов приходят с именем файла
и причиной, и по ISSUES 2.10, 3.1, 3.5 видно, что дисциплина «найди строку, которая врёт»
применяется. Ось bounded/ambient проведена последовательно: `post` через процедуру с двумя
портами, `model.json` как видимый люк, команды без произвольных процедур. CLAUDE.md как журнал
отказов, а не документация, это и есть то, что делает «код как compile target» правдой.

**Вид как ось диспетчеризации.** `EndpointKind` переключает `ToSqlSchema`, `SetDefaults`,
`TableDefaultColumns`, `IndexToolbar`, `CreateEditTemplate`, `HasPeriod`, `FilterMetadata`, и CLAUDE.md
называет это «кривизной в грамматике C#». Но 1.2 показывает, что дело не в грамматике: шаблон
карточки разделён на «документ/остальное», хотя вопрос «есть ли `computed`» задаётся декларации, а
не виду. 1.14 (`BrowseToolbar` забыл про вид), 1.9 (`TransName` своим правилом): та же причина.
Там, где ответ уже лежит в декларации или в shape (`Declaration.Rules`, `ColorColumn`,
`Posts().Any()`), код это делает правильно; там, где остался switch по виду, он отстаёт на каждый
новый вид. Направление, уже выбранное для трейтов («колонка типа X, а не trait»), стоит довести до
генераторов: спрашивать «что объявлено», не «какого ты вида».

**У сгенерированного нет своего beam.** Признано (save без теста, print последний), но 1.x
показывает цену: 1.3, 1.4, 1.5, 1.8, 1.13, 1.19 живут в генераторах, и валидатор проверяет, что
генератор не бросил, а не что вывод верен. ISSUES 6.9 уже зафиксировал закон: «что генерируется, то
и рендерится» держится только там, где сгенерированное кто-то прочитал обратно. Пока это так,
обещание «drift visible and cheap to catch» выполнено для файла автора и не выполнено для
собственных генераторов. Единственное место, где стоит поменять приоритет: раньше следующего
вида, а не после.

**Словарь впереди механизма.** `Number`, `Policy`/`Sql`, `Audit`, `Attachments`, `Copy`, `Show`
приняты enum'ом и схемой, реализации нет, отказа нет (1.1, 1.12, 1.18). Против собственного «don't
build» с другой стороны: слово заведено раньше читателя. Правило на одну строку: слово входит в
enum вместе с первым читателем или с отказом на загрузке.

Остальное (копии `ByKey`, `StateDefaultColumns`, ledger/turnover) гигиена; она отстаёт от документа
ровно потому, что документ получает больше внимания, чем код, в который он компилируется. При
такой философии ожидаемо и чинится по одному.

## 6. ERP на метаданных: что не хватает

«Чисто на метаданных» не бывает ни у кого: 1С, единственное живое доказательство, это метаданные
плюс модули с императивным кодом на каждом объекте. CLAUDE.md уже сформулировал правильную
версию: метаданные плюс коробки с объявленными портами; `post` через процедуру с `@Id`/`@UserId`
такая коробка. Вопрос не «можно ли без кода», а «хватает ли типов коробок». Сегодня их две
(процедура проводки, JS-выражение в `computed`) плюс `model.json` как люк, помеченный как люк.

**Есть:** учётное ядро целиком. Справочники, документы со строками и видами, операции, журналы,
главная книга с планом счетов, проводка двух видов, нумерация, состояния, печать, четыре отчётные
формы, деплой, тесты через сценарии.

**Нет, в порядке того, насколько блокирует:**

- **Документ из документа.** Счёт → оплата → отгрузка, «ввод на основании». ERP это в основном
  цепочки документов, и сегодня они невыразимы ни в файле, ни глаголом. Декларативная коробка того
  же типа, что `post`: маппинг из шапки и строк одного документа в другой. Самая важная недостающая
  вещь.
- **Второй императивный глагол.** «Пересчитать», «заполнить по остаткам», «распределить»:
  процедура с объявленными портами, вызываемая кнопкой, не только проводкой. Переходы состояний
  из той же серии и уже спроектированы.
- **Права.** В `model.json` они есть, в `metadata.json` нет (todo.txt 34). Без ролей и ограничения по
  организации это не продукт.
- **Отчёты произвольной формы.** Четыре встроенных покрывают регистры; произвольный отчёт с
  группировками по любым колонкам это пятый вид или `$sql`-поверхность с объявленными фильтрами.

**Реальный риск: формы.** «Целиком или ничего» верно как принцип, но у ERP сотни экранов, и
большинство отличаются от дефолта одной группой полей. Пока форму нельзя получить текстом (ISSUES
3.6, первая ступень), каждое отклонение это либо «набрать всю форму с нуля», либо уход в
`model.json`. Во втором случае «на метаданных» тихо превращается в «половина экранов на
metadata.json, половина в vxaml», и beam теряет ровно те экраны, которые правились руками. Эжект
формы в JSON важнее любого нового вида.

**Порядок:** эжект формы, документ из документа, права, второй глагол. Объём каждого сопоставим с
тем, что уже сделано для `post` или `state`. Что не ляжет в метаданные, ляжет в коробку с портами;
это не поражение принципа, а его формулировка.

## 7. Производительность: где затормозит

Форма сгенерированного SQL правильная: set-based, параметризованный, постраничный, ссылки
разрешаются одним `@map` без N+1. Проблема не в архитектуре и не в новых видах. Исходный факт: DDL
создаёт `PK_{table} primary key (Id)` и FK-констрейнты и больше ни одного индекса
(`CliDatabaseCreator.cs:57`; `TableMetadata.Indexes` только у accplan). Всё ниже из этого.

1. **Распроведение и гашение, раньше всего.** `delete from jrn.X where [Document] = @Id` без индекса
   на `Document` = скан журнала на каждое распроведение, внутри транзакции. `DbRemove` делает
   `exists(... @Id in (r.[Agent], r.[Payer]))` по каждой ссылающейся таблице, тоже без индексов.
   Журнал растёт быстрее документов (строки × журналы): заметно на единицах миллионов строк
   журнала, секунды на клик плюс блокировки.
2. **Открытие списка документов.** `a.[Date] >= @From and a.[Date] < @end` (`SqlBuilderIndex.cs:150`)
   без индекса на `Date` = полный скан таблицы документов на каждое открытие. Период по умолчанию
   `getdate()`, то есть узкий, но искать один день в 10M строк без индекса это те же 10M: 1–2 с на
   тёплом кэше.
3. **Сортировка справочника.** `order by a.Name ... offset/fetch` без индекса на `Name` = сортировка
   всей таблицы на каждую страницу; по представлению ссылки (`r1.[Name]`) то же после join.
   Заметно с миллиона строк в контрагентах или номенклатуре.
4. **Поиск по фрагменту.** `like N'%x%'` по всем searchable колонкам и представлениям ссылок
   (`:194-195`). Индекс не помогает в принципе; на 10M документов секунды. Ответ full-text, это
   другой уровень цены, и решать не сейчас.
5. **Отчёты.** Скан журнала/ledger от начала времён. Ответ nonclustered columnstore на `jrn`/`led`,
   одна строка в DDL-генераторе; таблицы итогов как вид не нужны. Замечание: `(@X is null or
   j.[X] = @X)` в фильтрах отчётов мешает seek'у даже при индексе, с columnstore неважно.

**ОТЛОЖЕНО до реального трения (решение автора 2026-09-26).** Правило «индекс на каждую FK-колонку»
отклонено: большинство FK никогда не ищется, а индекс на неищущуюся колонку стоит каждой вставки и
не покупает ничего. Индекс заводится под медленный запрос, который назвал его колонку, — не
заранее и не общим правилом. Список выше — диагноз на тот день: какой запрос что ищет.
