> Platform-wide goal and working method: [/CLAUDE.md](../../CLAUDE.md). Open issues and design debts: [ISSUES.md](ISSUES.md).
> Analysis of the package, 2026-09-26 (findings by line, the approach, ERP on metadata, where it slows): [REVIEW-2026-09-26.md](REVIEW-2026-09-26.md).

## Declarations: rules by kind, layered by "mine wins"

One `metadata.json`, deserialized twice: `TableMetadata` (the shape), `DeclarationMetadata` (what this endpoint declares about it). Not a partition of the file — a key sits in both only when it answers two different questions, and today one does: `table` ("was it written" / "what is it"). Otherwise "where do I read this from" comes back. Decided 2026-08.

- **A rule is keyed by KIND, not by field.** `required` = names, `visible`/`computed` = field→expression, `inherit` = field→source; each kind carries its own shape, so a parameter cannot be orphaned and a new kind widens nothing shared. Field→bag-of-rules failed twice on this: a bag has a level where `applyIf` guards nothing.
- **Layering is one sentence — mine wins — and one implementation** (`RuleMetadata.Merge`, on both axes: storage under operation, collection under row kind). **Lists union**: a list on the layer that speaks about everyone states something about all of them; a requirement that does not hold for all is written in the wrong layer. Overriding failed silently, unioning fails loudly — as a validator visible in the generated template. **Maps override by key**, which makes partial commonality writable: two kinds computing `Sum` alike and a third differently = one formula plus one override.
- **The far half of a reference resolves late; that is what keeps the bake early.** A rule's own columns are findable as the declaration is built; a column of the target table needs the reference graph, linked only after publication because it is cyclic. So `inherit` keeps `Source` as a name and `RefMapBuilder` resolves it when emitting SQL. Eagerly would push the bake past publication and leave the endpoint mutable for one field.
- **Declared and resolved never share a field.** `Forms` = written by the author, `BakedForms` = resolved by the bake. One collection in both roles hands out whichever was written last — how a declared form once reached the generator with no columns looked up.
- **The bake rebuilds, never fills.** A node it walks may belong to another, already published endpoint (an operation with no rows or form of its own gets the storage's by reference), so writing into it would write into someone else's declaration. Every level returns a new record (`with`).
- **`storage` is a second address over one table, and not only for operations.** A catalog or a journal may point at another's shape the way an operation points at its document: one table, one `TableMetadata` instance, no deploy of its own, the declaration layered on top - and screens of its own under its own URL, which is what `$meta` and materialize then work in. An operation adds one thing this does not: a code in the rows. Without `fixed` (below) this is a second WINDOW on the same rows. A reference may target the second address: same foreign key, a different picker. Sets stay out - no screen, so a second address to one would address nothing. Decided 2026-09.
- **`fixed` says which SUBSET an address is about, in one key with two derivations.** `"fixed": { "IsCustomer": true }`: the rows carry these values (the WHERE of the index, and of the fetch a selector types into - two roads to the rows of one address, so one predicate, `SqlBuilder.FixedPredicate`), and a new record starts on them (a literal initial, folded into `Initials` by the bake - every reader of initials reads that and not `InitialValues`). Not only WHERE: without the initial the first record created under the address vanishes from it on save. The card is not filtered (`where Id = @Id`), as an operation's is not - a foreign id in the URL opens. The value is spelled by the COLUMN, as a literal initial is; a field cannot be both fixed and given an initial; the form is untouched - the field stays an ordinary control, and unticking it moves the record out of the set, which is data. `where` was refused as the name: it explains the predicate and not the initial. Decided 2026-09.
- **Driven from the shape, so the result is total.** Every collection gets a node, every row set an entry, mentioned in the file or not — the difference between "nothing was declared" and "nothing is declared", and what deletes the `if (declared == null)` every generator carried.

## System endpoints: behaviour is a type, not a kind

Addresses served by the platform itself: no `metadata.json`, no declaration, no generated forms — screen, data and save are code. Two: `/tag/settings` (edits an entity's tags) and `/operation` (registry of operation codes, one `browse`). Decided 2026-08.

- **A subtype of `EndpointMetadata`, turned into a builder at one seam.** Shape set by `ReportEndpointMetadata`: not a data endpoint, own builder, chosen by what it *is* — no string travels loader → dispatcher → back. The seam is `ModelBuilderFactory.BuildAsync`, the only place knowing the kinds; everything above holds one `IModelBuilder` and asks.
- **The builder contract refuses by default; only `Path` is required.** Every action on `IModelBuilder` defaults to throwing `'{action}' is not supported for '{path}'`, so a builder declares only what it serves. Not an abstract base with throwing virtuals: a default interface member is reachable through the interface and never through the class, so a concrete builder's surface stops claiming six things it cannot do. `Path` is undeclinable — every refusal is worded with it.
- **Not an entry in `TableMetadataDefaults.SystemTable`.** That registry answers "which table stands behind this address" and returns a shape; a behaviour has none, so an entry means fabricating a `TableMetadata` — the same category error as a `ColumnType` for something not stored.
- **`Kind` is set literally; `EndpointKindOf` is not taught the namespace.** It answers "what did the FOLDER declare", and no folder declares this. Teaching it would flip `DeclaresShapeSource`, demanding a `table` key from an endpoint with no file to write one in. The endpoint is recognised before the file is read.
- **What the container carries is decided by the second case, not the first.** The tag dialog carries only its address, written on the type, so the control opening it and the builder serving it cannot drift. The operation registry carries a **shape**, because it is pointed at — every document's `operation` column resolves to it. Hence `IRefTarget`: the two members (`Storage`, `Path`) every reader of `RefTable` asks for, so widening the field moved no call site. A report does not implement it — it owns no data to point at.
- **A code-declared table ≠ a system endpoint.** `TagsTable()` and `OperationsTable()` stay; the deploy and the builders read them. System means *the endpoint* is described nowhere. Once both addresses had their own types, `TableMetadataDefaults.SystemTable` had nothing left to answer: it existed only to give a code-declared table an address inside the file pipeline, and a system endpoint gives it one directly.
- **Leaving the generated pipeline removes a class of bug, not just a page.** `ColumnType.Operation` means both the identity of an operation (key of `doc.[Operations]`) and a reference to one; `IsRef` says yes to both. The generated index met only the second until asked to render the registry, and threw on its own key. Not patched — the page left the pipeline and the ambiguity became unreachable.
- **The guards were already there.** `GetNormalEndpointAsync` throws "is not a data endpoint"; `ResolveReferencesAsync` names the type and throws on an unknown one. Asking a system endpoint for a shape fails in one place, loudly — what makes "no shape" safe rather than merely unwritten.
- **The address obeys the same grammar as everything else.** Two segments (`ParsePath` takes no more, so `catalog/tags/settings` silently loses its tail); the second is a noun, because `edit` names an action everywhere else. Identity rides in the query (`?For=Agent`) — the one place the usual rule inverts: the path is lower-cased and a single segment cannot address an entity in a two-segment namespace.

## Forms: whole or nothing

A form is per **endpoint**, not per shape — an operation and its document storage are one table and two screens. So `forms` lives in `DeclarationMetadata`; `TableMetadata` stays the shape alone. Decided 2026-08.

- **A declared form replaces the default entirely**, never node by node. A partial override adds an invisible second question at every node ("instead of, or on top of?") that the file cannot answer, so the model guesses per node. A declared form must be readable without holding `DefaultFormBuilder` in your head.
- **Across endpoints it layers by form key; the value is all-or-nothing.** A form is a tree of unnamed nodes — nothing inside to address. An operation declaring its own `edit` still shows the storage's `index`.
- **Declared and default take the same walk**, eagerly, while the endpoint is built: a wrong form fails the load, where a throw publishes nothing, instead of at the first request. The lazy path is what let a declared form reach the generator unresolved.
- **A tab strip is a screen, so the state it drives belongs to it.** `$$Tab{the first tab's row set}`, written by the bake onto the node (`FormElement.TabState`) and read by both the XAML and the template. `$$Tab{collection}` could not name a strip over two collections, and that — nothing in the model — is what used to refuse one: everything else the strip draws (case value, active value, badge, add-row) already took the row set from the tab. So the default form puts every row set of the record under ONE strip, kinds of a collection and collections alike: they are the same thing to a screen, mutually exclusive views of what is inside this record. A strip per collection gave stacked bars of one tab each, splitting the height, and a document with six collections read as six sections. What the removed check guarded is now guarded where it belongs: two tabs on one row set, a strip with no tabs, a tab with no `scope`, anything but a tab inside a strip. The template stops declaring a state property per collection and declares one per strip — one too few for two strips over one collection, one too many for every collection no strip shows. Decided 2026-09-20.
- **Price: the default must be obtainable as text.** "Whole or nothing" means "type it from scratch" until it can be ejected — the eject is owed, not optional. See [ISSUES 3.6](ISSUES.md).
- **A node refuses a key nothing reads** (`FormElement.CheckElement`, on every node while the form is baked). `is: filters` carrying `fields`, a toolbar carrying `elements`: the node rendered, empty, and the author wrote the same thing into the next place — the one failure of this format that leaves no trace at all, and the only one a model pays for three times before guessing. The table of what each kind reads is a second reading of `XamlBuilder.ElementToControl` and of nothing else; a kind absent from it is one whose content is not described yet, and nothing is refused on it. Only the list-valued keys, because only they can be told from an absent key — `axis` and `labelAt` default to their first member, the same reason `kinds` is examined for emptiness alone. This is where the next such rule lands, one line at a time, as friction finds it. Decided 2026-09-20.
- **A group lays out members and groups alike:** `fields` are the editors it carries, `elements` the groups under it — a row of two columns is one inside another, and that is the ordinary way to lay out a card. Until 2026-09-20 the renderer read the members alone and dropped the rest silently. Fields come first, because the file is read top to bottom and they are written first; two keys cannot interleave, so the order is decided once in the builder rather than guessed per form.

## Commands: a derived set, plus what the endpoint declares

A command is not screen content. The form carries **references only**; definitions live on the endpoint — as `post` already does. Decided 2026-08; the bar reworked 2026-09.

- **One namespace per endpoint: platform entries plus author entries.** Platform entries derive from the kind, `traits`, `post`, `printForms`, `basedOn`; author entries are declared. A collision is an error — that is how "a standard command may not be overridden" is enforced, by one name check rather than a rule the form carries. An overridable standard name stops meaning anything: reading a form would no longer tell you what `delete` does.
- **The standard bar is the template's, not the form's.** Every screen shows its derived set (`XamlBuilder.StandardToolbar`); no form hides a command. Whether a command exists is the endpoint's question (a catalog filled by an integration has no `delete`); a hidden button would leave that fact true everywhere else. Not declarable yet (ISSUES 3.7): the catalog bar is fixed by the kind; when the fact arrives, SQL, selector and bar learn it at once.
- **The form's `toolbar` slot adds, in one place:** between the entity's commands and the chrome tail (`$sep, Reload [, aligner, Search]`), behind a separator of its own. The place is the template's, so the list has one bar token, `$sep`; `$toRight` is gone. A standard name in the slot is not an error — it is a second, visible button.
- **A `Toolbar` node in `body` is a second bar** of the author's own commands. The edit dialog has no bar, so a `toolbar` slot declared on it fails the load.
- **No ambient hatches.** An author command composes declared verbs: navigation or a dialog onto an endpoint that must exist, or a verb the endpoint declares (today one — `post`). New kinds of action enter by the platform declaring a verb, once, not by each application naming a procedure. So a data-changing action that is not posting is not expressible yet: the verb list is short in the right place, and grows by decision.

Nothing is left to run time: a reference resolves to an endpoint entry, an entry to a verb and an address that exists.

## Members: a form node shows members, not columns

`fields` stays a list of names; a name resolves to a `MemberDescriptor` — a column, or something a trait contributes. Today one of the second sort: `Tags`, rows in their own table, reaching the model as an array. Decided 2026-08.

- **Not a `ColumnType.Tags` on a fabricated column.** `ColumnType` answers "what is stored in this column and how" and feeds `SqlDataType()` for DDL; tags are not stored on the table, so that member is an enum value with no SQL type — a hole held shut only by nobody handing it to the wrong function. Cheaper by three mechanical call sites, and structurally unguarded. The same fabrication was already removed once, from the old `TableFilters()`.
- **The candidate list is built per form, not by a predicate.** `DeclarationBake.BuildForms` is where the three forms already differ: `index`/`browse` get index columns, `edit` gets edit columns plus `Tags`. A predicate on `TableColumn` cannot express a non-column member, and spreading the trait check across the walk puts the answer in two places.
- **The index grid keeps its splice.** Tags render as a second line inside `Name` — a trait changing how a column draws, a different act from a trait adding a member. Both would give one thing two places to be.
- **`Tags` sits in two namespaces with two meanings.** Member: the record's own tags, bound to `{Model}.Tags`, editable. Filter: `Parent.Filter.Tags`, candidates from the root recordset. Two entries, two controls — why `Filters` stays its own property instead of collapsing into `fields`.

## Filters: a namespace on the shape, referenced by the form

Never a field list: three of four kinds have no column (`Fragment`, `Period`, `Tags`), only ref filters borrowed one. So filters are their own namespace, derived from the shape; a form carries references into it. Decided 2026-08.

- **The kind is how a filter lands in the WHERE, not what draws it.** Control and `DataType` follow from the kind. Anything that is not equality on a column of the table is a new kind, once — then namespace, SQL and panel learn it together. A boolean Yes/No/All is one enum member plus one line.
- **Three consumers that do not see each other:** the index SQL, the CollectionView's `FilterDescription`, the taskpad panel. Only the panel goes through a form, and only as references — a form can hide a filter, never invent one. The namespace is derived from `TableMetadata` and the endpoint's declaration together (`Filters(table, declaration)`), because one column can mean different things over one table: the operation column is a selector over every operation at the storage, a set-like choice among the document's own where it lists `operations`, and absent where the address IS the one operation. Every consumer holds the declaration; the bake hands the namespace to the form with its members. It becomes declarable the day a filter does — not before. Decided 2026-09-26.
- **SQL cannot follow a form.** One index procedure serves `index`, `indexpartial` and `browse`, and the last has its own form: following a form means choosing which to believe, or writing two procedures.
- **No collision check between platform names and column names.** Tried and removed: guarding two names of ten inside the namespace builder was worse than guarding none — it read as an invariant while being disabled by reordering two lines. A ref column named `Period` gives two controls on one Filter property, visible on the first page load.
- **The SQL parameter space is split instead of checked.** A parameter named after an author's column - a ref or set filter, a role, a picker's owner, a report filter - is `@$<name>` (`SqlExtensions.ColumnParam`); the platform's own (`@Order`, `@From`, `@Offset`, `@Fragment`, `@Tags`, …) stay bare. A column name cannot hold `$` (`CheckNames`), so the two cannot meet. It was reached by the first reference column called `Order`: the index declared `@Order` twice. 2026-09-30.

## Storno: what adds up is negated

`"storno": true` on a mapped leg writes the movement negated in the same direction. Which columns it negates is one predicate, `TableColumn.IsAdditive`. Decided 2026-09-26: a list of "measures" kept beside `ColumnType` had drifted, and the first `storno` over `Qty` would have written positive quantities.

- **Negated: `Amount`, `Qty`, `Money`** — values whose sum over rows means something. `Direction` never: the leg keeps its side.
- **Not negated: `Price`, `Percent`, `Factor`** — rates. A reversed row keeps its price; its quantity and amount carry the sign.
- **Not negated: `Float`, `Decimal`.** Numbers without business meaning, and the platform does not guess one for them. A column meant to flip is declared `Amount` or `Qty` — the type is where the author says it adds up.
- **The question is "does it add up", not "is it a number".** Alignment and column role ask the second — `IsNumber` (XamlExtensions); the format splits on `IsCurrency`: `Amount`, `Price`, `Money` show two decimals, `Qty` as many as it has.

## Computed columns: read by all, written by none

`"sqlAs": "<T-SQL>"` on a field makes the column `as cast((<expr>) as <type of the domain>)` (`TableColumn.SqlAs`, `HasSqlAs`, `SqlExtensions.SqlAsDefinition`). The chart's `DisplayName` (code + name, its `DisplayAs`) is the first user, declared in the baseline the way an author declares one. Decided 2026-10-02 (skill: `metadata.md` → the invariants of a field).

- **A column, so every reader is unchanged.** `Presentation` is an identifier inside SQL (map, fetch, search, a reference column in another grid); an expression there would have rewritten each of them. `derived` (`$X`) is not a column and stays out of these positions.
- **Not `computed` - two layers, two words.** `rules.computed` is the form's: a Vue computed (a getter, maybe a setter) over a column the save writes. This one is the database's and nothing sends it. One word for both, told apart by position, was refused: beside `this.Qty * this.Price` in `rules`, a model writes JS into the database key by analogy. `sqlAs` names the language and the T-SQL it ends up in (`[X] as (...)`). They may coexist on one field, the author keeps the two expressions in step.
- **The cast makes the declared type the stored one.** Without it the database infers its own (`nvarchar(64) + nvarchar(255)` is 320), and the seed would carry a type the column does not have. Price: a longer string is truncated silently - the author sets `length`.
- **Written by nothing; named as a target, refused at load.** Out of `IsSentColumn` (table type and DataTable), `IsFieldUpdated`, the details merge, the birth's inserts, journal auto-mapping. Refused: `initialValues`, `fixed`, `inherit` into it, `basedOn.document`, a posting's `document`/`row` or a ledger leg, a seed row. No default and nullable whatever the domain - the value is the expression's.
- **The birth computes it too.** The table variables declare it with the same definition, so a card born on basis shows it before the save.
- **The expression is not parsed.** A wrong one fails the deploy. Only its own row: SQL Server refuses a subquery there.
- **Added, never altered.** `a2meta.Columns.[sql_as]` carries the text (so a new one moves the hash), `SyncSchema` adds it in a statement after the plain columns - the expression may read columns added in the same run. A changed expression of an existing column is not applied: the catalog keeps it normalized, the seed is overwritten before `SyncSchema`, so there is nothing to compare with. Deferred.
- **Shown read-only:** `Static` in the card and in a row.

## Shown and chosen: `presentation` and `displayAs`

A reference is either SHOWN (a cell of another index, the transactions of a document, a blank) or CHOSEN (a selector in a card or a row, the filter's selector, the combo of a set, the text typed to find it, the model's find). Two keys, one per kind of place: `presentation` and `displayAs`, the latter defaulting to the former. Decided 2026-10-03 (skill: `metadata.md` → `presentation` / `displayAs`).

- **Both, because one column could not answer both.** A chart is read by its code in a list and chosen by code and name; with one column the ledger's Acc/CorrAcc became 'code name' everywhere. Every place knows which of the two it is, so nothing decides at run time.
- **One element carries both.** `Name` is the presentation, as it always was; the choice column rides beside it under its own name (`SqlBuilder.ChoiceField`, through `RefFields` - the map, the candidates of a set, the fetch and its maps). Under its own name and not a `$` member, because an element picked in the browse is a row of the target itself and has the column already. A control of choice reads `TableMetadata.ChoiceProperty`, which is null when the two keys are one column: then the choice is the element's `Name` - nothing to carry, nothing to write, the control's own default. Written into an ejected view, `DisplayProperty="Name"` would sit on every selector. So: a selector and the combo of a set in a card or a row take `DisplayProperty = ChoiceProperty` (the combo without an item template - its default value is the element itself, which is what they hold); the filter's combo (its value is the code, `value-prop`) and the state picker (no `DisplayProperty`, the template is its only way) keep the item template and spell `?? Name` there, where a path is required.
- **`displayAs: "Name"` with another presentation is refused at load:** the element's `Name` is the presentation, so the two would be one property.
- **Allowed wherever `presentation` is, sets included** - an enum or a state is an ordinary table and may have columns of its own. Refused where `presentation` is (a journal): nothing references it.
- **The fetch searches and orders by the choice column; the index searches a reference column by the presentation** - what the cell shows.
- **Not reached:** the selector of a report filter (its value is built by the report builders), the operations list (a registry with Name only).

## NOT NULL: the domain's zero

A column is `NOT NULL DEFAULT 0` exactly when its domain has a zero — one predicate, `TableColumn.HasZero`; there is no `default` or `notNull` key on a field. Decided 2026-09-28 (skill: `metadata.md` → «`NOT NULL`»).

- **A zero: magnitudes and the flag.** `Amount`, `Qty`, `Price`, `Percent`, `Factor`, `Money`, `Decimal`, `Float` — 0 is none, not unknown; `Boolean` — false is 'no'. Plus the platform's own `Void`, `Done`, `IsSystem`.
- **None: a key, a code, a reference, a date, a string** (`Integer`, `BigInt`, `Ref`, …). Their 'nothing' is an absence, carried by NULL.
- **By meaning, not by the client.** The client sends 0 for every number, but also '' and a zero date — asked that way, NOT NULL would spread to everything.
- **`Factor` is 0, not its neutral 1.** A rate of 1 in a new document is the author's (`initialValues`); DEFAULT 1 would reach only an insert past the platform, since the client builds a row with 0 and the merge writes every column.
- **A statement that names such a column with nothing for it writes the zero** (`EmptyLiteral`): the ledger leg that does not name a measure, the seed row that does not name a column. NULL there is refused.
- **No `Bit`, no `Number`.** `Bit` was `Boolean` spelled by SQL; `Number` never had an SQL type, and `Decimal` is the number without semantics.

## Posting by procedure: a box with two ports

Some postings are not a column mapping — a cost calculation reads the journal it is about to write, which no `document`/`row` pair expresses. So `post` has a second spelling: `sql: { post, unpost }` plus `journals`. Not the ambient hatch Commands refuses: a procedure is imperative code in a box, and it is a box because its ports are declared here rather than reached for. Decided 2026-09.

- **The journals are declared even though the procedure writes them.** Nothing can read them out of a procedure, and two consumers need them: the transactions dialog, and the unpost when unauthored. A journal named here carries provenance (`ColumnType.Document`) whoever writes it, keeping "what did this document post" answerable without reading SQL. An unverified promise — the whole price of the second spelling, named exactly, in one place.
- **`unpost` is optional; the derived delete is the default.** A procedure that wrote the provenance is undone by the same delete as any posting. Write it only for an inverse that is not a delete — a reversal keeping the rows.
- **Two ports, `@Id` and `@UserId`.** Anything more is a fact taken without being declared; the rest is read from the document handed in. The line between "imperative inside a box" and ambient authority is drawn at the parameter list.
- **The transaction and the `Done` flag stay the platform's.** `begin tran` → `update Done` (which IS the lock) → `exec` → `commit`. So the procedure never meets a second caller and cannot be asked to be idempotent, and the document is already in its target state when it runs. It does not own the transaction: `commit` there only decrements `@@TRANCOUNT`, `rollback` kills the outer one and makes the platform's commit fail far from the cause — so failure is a `throw`.
- **One `sql` entry, never mixed with mapped legs.** Half-platform, half-procedure cannot say which wrote a row, and its unpost has no order to undo in; two procedures bury the same answer in a file. Two are written as one calling two, where the order is visible in code. Refused at load, in one check.
- **The procedure name is verified nowhere.** Deliberately: the first posting exercises it and fails loudly, unlike a mapping typo sitting under a button nobody presses while developing an index page. Checking it costs a deploy-time round trip over a walk that collects only shape-owning endpoints, and buys a message the database already gives.
- **Nothing outside changes** — commands, `$invoke('post')`, the buttons bound to `Done`, the dialog. The test that the seam was cut right: `PostStatements` hands out the BODY of the two statements; the frame is written once.

## Transactions: a projection of `post`, not a screen

`ShowTrans` shows what one document put into the journals, all of it derived: tabs = the journals `post` targets, rows = found by the provenance column posting already requires, columns = the journal's own. No form, no `forms` key — nothing an author could say that `post` has not. Decided 2026-08.

- **Its own projection, not the journal's index embedded.** Rejected: `Include` on the journal's `indexpartial` with `?Document=<id>` — no SQL at all, page and filter exist, paging and sorting free. It fails on what this screen *is*: the projection drops what the document fixes, and that difference belongs to the pair (document, journal), not to the journal. On the journal side it needs a flag saying "I am embedded" — a screen whose appearance depends on who opened it, ambient authority wearing a parameter.
- **A column the document FIXES carries no information here.** `Document`, `DocumentType`, `Date`, `Operation` — dropped by `ColumnType`, not by the post mapping. "Filled from the header" is a different question and answers wrongly: a journal's `Agent` also comes from the header, is equally constant, and is exactly what the dialog is opened to read. The wider rule — any column pinned by an equality filter — was refused: on the journal's own index the filter is visible and clearable, and a column vanishing as you pick one is a worse screen. Right here only because the filter is fixed by context, with no control to change it.
- **A journal is called by its FOLDER — not `Model`, not `Table`.** One word names the array, the row type, the tab's switch value and the localization key; drift between them is a tab matching no case. `Model` is a shape several journals may share, so `Transaction` would name two different arrays of two different column sets in one model. `Table` is where rows are stored (`jrn.StockJournal`) and renames only through a migration. The folder is what the address calls the thing, and what `TableMetadata.SetDefaults` PascalCases into the default `Model`.
- **The ref map spans several tables.** The WHERE lives on `RefMapItem`, not in a conditional over `SourceTable.Kind` inside the insert generator: one `@map`, one resolve per target, so a catalog three journals point at is fetched once. The columns are a parameter for the same reason — a map resolves what a recordset SENT, and taking them from the table refetched the journal's `Document` on every row of the document you are standing on.
- **Slots come from the widest source, not the first.** Naming `@map`'s columns after the first source and reaching past its end for the rest is an index out of range: unreachable while a header out-numbered its details, reachable the moment several tables are unioned, where nothing orders them.
- **Posting commands exist when the endpoint posts.** `Post`, `UnPost`, `ShowTrans` — one group with its own leading separator, emitted only for a declared `post`, which is why the default form builder is handed the declaration and not only the shape. Without it a document that never posts carries three buttons into a screen with nothing to show.

## References to a document: a view per table, carrying the address

A reference to a document resolves to `Id`, `Name`, `Done` and `$Url` — where it opens, so a click on a journal row opens the document that posted it. Read from `<schema>.[<Table>$Ref]`, deployed by `CreateRefViewsScript` right after `SyncSchema` (a view binds to the columns that exist when it is created). Decided and built 2026-09-27.

- **The address is the DOCUMENT's, never the storage's or the operation's.** A `receipt.supplier` row opens `/document/receipt/edit`: the document reads its operation from the row itself. Over a shared storage the row's operation says whose it is (`left join doc.Operations` on it); a table with no operation column is one document and its address is a literal.
- **The registry keeps the document twice: `Document` (name) and `Path` (address).** They differ under an alias — `invoice` is `/sale/invoice`, and nothing rewrites `/document/invoice` to it (`KindFolders`). The name is what a document compares its own rows by; the address is where a reference opens. Replacing the name by the path was refused: both are wanted, and the registry is a hundred rows.
- **A view and not an expression in the resolve.** A subquery in `RefFields` keeps it one output, but only the generator sees it. The view is one place for every reader — the map, the `Document` dimension of a mart (`(Name, Url)`, concepts/mart), `sql: { post }` procedures, BI. Not a `union all` over all document tables: ids are per table, and the client map is keyed by `Id` alone.
- **`$Icon` is how the reference draws, and the view is where it is decided** — `success-outline-green` posted, `warning-outline-yellow` not (without the colour suffix they draw blue), the platform's icon name stored as a colour is stored as a class. `Done` stays beside it: the fact for logic, the icon for the eye, one column behind both. In a journal it is always green — a journal row exists only for a posted document — and that is wanted: it marks the cell as a document.
- **`$Url`, not `Url`.** No name from a file can take `$` (`CheckNames`), so no author column meets it; the client's `toJson` drops `$` members, so it never travels back. `Done` stays unprefixed — it is a column.
- **Which table a reference reads is a property of the target** (`TableMetadata.RefSourceName`), so `RefMapBuilder` asks and does not branch. The TS type promises `$Url` by name (`ScriptBuilder.RefTsProperties`): it is not a column, so `TsProperties` cannot see it.
- **In a grid the cell is a link, wherever the reference is shown** (`IndexPageXaml.DocumentLink`): `Open` with `Url={Bind X.$Url}`, `Argument={Bind X}` — `$navigate` takes the `$id` itself. Chosen by the target, as the badge is; before the badge, because opening is behaviour and colour is dress. `If` on `Id`: an empty link would open `/edit/null`. The journal's own `Edit` still opens its row.
- **The view reaches a database only when the hash moves, so its members are in the hash.** Its text depends on the table's columns through `a.*`, and those are in the seed. What it adds is one list, `Constants.FieldNames.RefViewMembers`, read by the resolve, the TS type and the Xtra of every document table — adding a member moves the hash. On the document table and not the operations registry: a document with its own table has a view and no operations, and an application of only such documents deploys no registry. Hashing the whole view text was refused: views are generated, and a member is the only thing that changes in practice. What stays in the seed-blind class (Seed): an edit of an expression alone (another icon name) — move the hash by hand, or add it with a member.

## Print forms: paper under one act

A blank is not a kind — no window, no endpoint, no folder. `printForms` is a flat list on the endpoint's declaration: path to a file in a foreign format plus a title. The platform reads exactly one section of that file, `Model`, and hands the rest to a report engine. Decided 2026-08.

- **Per endpoint, never inherited from `storage`.** A blank is paper under an ACT: two operations over one table print different papers, and the storage has no act. So `printForms` is not named in `MergeDeclaration` — the same silence, for the same reason, as `post`.
- **No trait.** `TableTrait.Print` is gone: a trait lives on the SHAPE, and one shape shared by several operations cannot answer whether this one prints. A non-empty `printForms` is the whole answer; SQL, toolbar and menu learn it together.
- **One command; the screen is a parameter.** `Print` sits on both toolbars, `CommandScope` tells the builder which — the card hands it the record, the grid the selected row. Not two entries in `EntityCommandType`: printing is one act with two argument sources, and that namespace answers what the entity can DO. Not a lookup of the current action either — a button drawing differently depending on the caller is the hardest drift to see, so the two statically-known call sites pass it.
- **Depth is `RefId` + chained Maps, not dotted names.** A dotted property name carries exactly ONE type name (`FieldInfo`, `x[1]`) and the loader refuses a third segment (`DataModelReader.ProcessComplexMetadata`), so `Agent.TaxDepartment.Name` has no spelling there — and inventing one would DOUBLE the intermediate type under a name no other recordset uses. A Map row goes through `ProcessFields` like any other, so a `RefId` inside one makes the next placeholder and the next Map fills it: depth falls out of the mechanism. Order-free (`RefMapper` keeps a forward definition), a null reference yields an empty object, one agent behind fifty rows is fetched once.
- **One map per TABLE, over the union of every path onto it.** Two paths of a finite tree reach one table at different depths (a row's `Unit`, its item's `Unit`), so the map is built to a fixed point and regrouped each round. Emitting a table when first reached dropped the later path silently: a short map and a blank cell, no error.
- **Every column of every predicate is qualified.** A container's predicate is reused verbatim inside the subquery below it, and an unqualified name binds to the innermost scope that HAS such a column — so a column the inner table lacks becomes a correlated reference to the outer one. Silent wrong answer, not an error. Hence an alias per recordset, and a map's alias fixed to its table so the fixed point settles.
- **A collection is addressable under both names.** The declared key of `details` is every row; the composed name of a kind (`ServiceRows`) is that kind alone, own type and filter; a blank may use both. The one place the usual refusal of composed names inverts (`TableMetadata.ComposedRowSetHint`): the layout binds a `Range` to an ARRAY, and a scope-plus-kind pair has no single name.
- **`Id` is implicit, everything else is written.** Implicit only what the mechanism requires — nothing is addressable without `Id`, and both the Map merge and the master link key on it. `RowNo` is not: the paper wants it, the machine does not, and a second exception leaves a list to memorise.
- **`?Form=` names a declared blank, and is required.** Never a path from the client — that is a request for an arbitrary file. No first-blank default: a request that does not say what to print asks for nothing, and answering with whichever came first hands back a plausible wrong document.
- **The format of a blank is not the declaration's business.** The declared path carries no extension — it is named the way a view is — so which file it is, is a probe's answer (`PrintRequest.BlankOf`, with this layer's own candidate list — the engine gets the blank as a stream and never probes it), and what that file holds is the first byte's: a workbook in JSON, a page in XAML. The `Model` section is the same JSON in both, sitting where each format has room for it — a top-level key beside the layout, or `<Page.Model>` on the root. One grammar, so `PrintModel`'s tree parser never learned there were two formats; only where to find the text did. Decided 2026-09.
- **The layout is NEVER parsed** — not to build the fetch, not to check it: a cell calls functions and reads fields inside JS, so no reading of it could answer what to fetch. Price, real and accepted: a cell reading what `Model` does not carry renders empty and says nothing. Seen on the first printed page.
- **Not baked into the declaration.** Tempting, because forms are — but there the prize is failing at load, here it is negative: a typo in a peripheral blank would take down the document's index and card. What is left is caching, which one human click does not pay for. The viewer's host page loads only the record's `Id`; the blank is read once, by the report handler, when rendered.
- **A PDF layout failure is passed through as it is.** QuestPDF's `DocumentLayoutException` names no place, and its causes are many (a nested table, a picture, an unbreakable cell); we can count only columns, so a diagnosis would name an innocent place with confident numbers. Decided 2026-09-09.

## Autonums: a column and a key, never a trait

A document's number is an ordinary field the user may correct; the platform fills it on insert when empty. Which numbering the endpoint draws from is `autonum` on its declaration; what the numbering IS — pattern, period — is declared once, at `/autonum`. Decided 2026-09.

- **No trait; nothing added to `TableTrait`.** A column of `ColumnType.Autonum` is the whole answer to "is this numbered", as a non-empty `printForms` answers "does this print" — `TableTrait.Print` was removed for it. A trait would also have to ADD the column, and the platform adds columns only where it reads and writes them itself (`Parent`, `Folder`); a number is user data, written in `fields` next to `Name`. The author names it, the platform finds it BY TYPE, as with `RowKind` and `Operation`. Two such columns in one table is a throw: which one gets the number must not be a guess.
- **The check runs one way only.** `autonum` declared with no column of that type — throw. The reverse is legitimate: a column with no `autonum` is numbered by hand. The json schema's "required exactly when the storage declares a field of type Autonum" claims one direction too many.
- **Issued when the record first has the counter's whole key, and only if empty; the save frame is untouched.** Without a `Company` column that is the insert; with one, the save where the company goes from empty to filled (`deleted` vs `inserted` in the merge's output) - a draft saved with no company would otherwise draw from the no-company counter and repeat a number of the company it gets later. An event, not emptiness: a document whose company is already set is never numbered by an edit. The number travels in the TVP and updates like any field. No unique index: two operations over one storage may sit on different autonums, and their numbers legitimately meet in one table.
- **Gaps are accepted, not fought.** Numbering is never gapless in practice, and buying it costs the save an outer transaction plus a lock held through the whole save, details merges included. The number is issued on its own; a rollback eating one is the price.
- **The pointer is enum-shaped, not storage-shaped.** `"autonum": "waybill"` resolves to a VALUE inside `/autonum`, not to an endpoint — so the check has the shape `CheckLiteralInitials` already uses, at load, with no round trip. The address is the storage form (`SetDefaults` yields `/{schema}` on an empty table segment), and the key layers as everything else: an operation may number from its own, silence inherits the storage's.
- **The key in that file is `autonums` — zero new words.** Not `values`: the record is (id, name, pattern, period), and one key whose shape depends on the endpoint kind is two questions under one name. Not `series` (batch accounting wants that word), not `sequences` (`SQ_<table>` under every `Id` is already one), not `numerator` (a Russism; in English it is the top half of a fraction). `ColumnType.Autonum`, the declaration key, the folder and `doc.Autonums` already say this word. It reads by the enum's rule: address names the concept, key names the elements, pointer names one element.
- **The counter is split by the company, with no key for it.** A shared counter over several companies does not exist. `{p}` is only how the number reads: two companies with one prefix, or none, still count apart. The counters carry the company as `ColumnType.PlatformId` - no FK, as their `Autonum` column has none - so one application keeps its companies in one catalog, checked at deploy (`CheckOneCompanyCatalog`): ids of two catalogs would meet in one row. `{p}` is refused at load unless the endpoint's table has a `Company` column and its catalog one `Prefix` column (`CheckPrefix`, per endpoint - documents share a numbering and only some have a company).
- **The pattern is in the file; only the counter is data.** `{p}` is substituted from the company row at issue time, read by the caller (it knows the catalog) and substituted last — a substitution, not a reason to keep the template in the database. Declared, it leaves the deploy nothing to overwrite and the two sides nothing to drift on; the counter table holds counters only. A human-edited pattern is a different decision, arriving with the screen that edits it.
- **No `void` on an entry.** On an enum value it withdraws a candidate; nobody picks an autonum at run time — a file names it. A key deleted from the file keeps its row: the deploy merges without a delete arm (as the operations merge does), and documents carry the numbers it issued, so the counter must not restart.
- **The screen over the counters is not built.** An enum has no screen of its own — values are read through the columns pointing at them. A screen here would exist only for what the file does not hold: the current counter per period. Until wanted, `/autonum` is a file, a table, its rows, and the code issuing a number.
- **The file declares the numberings; its three names default.** One registry at one address, so schema, table and model default (`SetDefaults`) — written, they win. Rows land in the document schema: a namespace of its own is the ADDRESS, never where rows live. `ToEndpointKind` learns the folder because the kind must be set; `EndpointKindOf` deliberately does not — it answers "does this folder declare where its shape comes from", and this one does not, the same silence as `tag` and `operation`. The `schema == "autonum"` skip in `AllElementsMetadata` is removed: it skipped the one thing that now has to be deployed.

## Chart of accounts: a kind with a natural key and a seed file

`/accplan/<name>` — a table keyed by the account code, its rows declared in `seed.json` beside `metadata.json` and merged by the deploy. Design and the refused alternatives: `a2v10-md-skill/concepts/ledger/README.md`. Built 2026-09: kind, baseline, seed, deploy, the tree index and a read-only card. Not built: user sub-accounts (no create at all in v1), the `Account` domain. Decided 2026-09.

- **The key is `ColumnType.NaturalKey`, the column is still `Id`.** Same role as `Id` — primary key, never updated, `[Id!!Id]` — different domain: `nvarchar(64)`, no sequence. The role is `TableColumn.IsKey`, and every place that meant "the key" asks it rather than `ColumnType.Id`. Not a length facet on `Id`: a facet silently turning platformid into nvarchar is a discriminator nobody sees. Not `Key` (the category would share its name with one member) and not `Code` (taken).
- **A self link is spelled as the key of its own table.** `Parent` carries `KeyType`, set where the table is in hand (`TableDefaultColumns`); `ToSqlDbTypeInfo` takes it as its one platform-set facet. `Parent` gets a foreign key on its own table, for every kind — a catalog's `Parent` is never written by the save, so no existing row can break it.
- **`seed` is a key of every table, processed per kind.** Only `accplan` processes it; elsewhere the load refuses it, on `accplan` it is required. Everything is checked at load, without a database: keys against columns, values against the column's literal, the closed sets, the tree, no `.` in a code (it separates what a user adds). The rows reach the deploy hash through `Xtra`.
- **The merge is dumb and its arms are the rules.** A file row: `IsSystem = 1`, `Void = 0`, the columns it names — an author column not named by the row is left as it is (a `$`-bit per column). A row that left the file: `IsSystem = 0`, `Void = 1`, kept for the postings holding it. A row with `IsSystem = 0` is the user's and never touched. Emitted for an empty file too — emptying it is the last arm for every row.
- **`AccountType` and `NormalBalance` are stored by name, without a CHECK.** As `Period` is: the platform has no CHECK generation, and in stage 1 only the deploy writes these columns, from values checked at load.
- **`Split` is a fourth `NormalBalance`, not `Both` plus a key.** `Both` is one balance whose sign picks the side (441); `Split` is a debit and a credit balance at once, one per object of `SplitBy` (361). Netted, 361 hid receivables behind payables - the trial balance was wrong, not short. `SplitBy` sits on the account, not the ledger: it is a fact of accounting about 361, and on the ledger it needed a coverage rule, subtree inheritance and a legal `[]`. Price: every ledger over the chart has the columns (`CheckSplitColumns`). The file writes an array, the column keeps it joined by ',' - only the deploy writes it, so one spelling; the report and the checks read the file (`SeedRow.SplitBy`), since the list shapes a `group by` and a query is not composed from data. A leg with a literal `Split` account names every `SplitBy` column (`CheckSplitLeg`); a field account and a procedure are not seen. - **The index is a tree, and the tree is a form node: `is: treeGrid`.** Every screen goes through a form and a default form is a `FormMetadata` too, so there was no way around a vocabulary entry. Not refused on kinds without tree SQL: a guard designed ahead of use costs more to switch off than it saves. The default index of `accplan` is one `TreeGrid`, no pager, no filters; `Parent` is not a column there — the tree shows it.
- **The tree is read whole, parents first.** A chart is hundreds of rows: one select, no lazy expand, no `HasChildren` (`LoadAccountTreeModelAsync`). `ParentId` attaches a node to one already read, so a CTE counts the level from `Parent` and the rows go `order by Level, Id` — never an order read off the code, where a prefix is one plan's convention. A string `ParentId` links as a platformid one does.
- **A `CollectionView` exists only for a `DataGrid`.** It is what the grid reads through (`Parent.ItemsSource`, `Parent.Pager`); a tree binds to its collection directly, and a server-run view over it would ask for pages of a tree.
- **The closed sets travel as localization keys.** The tree sends `N'@[AccountType.' + a.[AccountType] + N']'` — a binding cannot compose a key; the card shows a `ComboBox` whose items are the enum's members under the same keys. Chosen by column name, on `accplan` only.
- **Read-only is `[!!ReadOnly]` of the system recordset, for any table with `IsSystem`.** The same slot a posted document uses (`a.Done`); a row the deploy writes is not edited by anyone. So the card is the ordinary edit dialog and nothing screen-side knows about seeds. The index bar has `Edit` and `Reload` only: nothing to create or delete.
- **`Parent` travels as `ParentElem` in the model.** `Parent` is reserved by the data model (every element's link to its container). The column keeps its name; `TableColumn.ModelName` is the one place that renames — select, binding, grid path, TS map. The save still reads `Parent`: harmless while the card is read-only, to be settled with user sub-accounts.
- **A natural key is headed `@[Code]`**, not the `#` of a surrogate (`TableColumn.Header`), and does not wrap in the tree.

## States: a kind for the set, a type for the column

A closed set of codes at `/state/<name>`, each value carrying a colour and a role in the lifecycle; a column pointing at one is `ColumnType.State`. Both, because they answer different questions. Decided 2026-09-18, built 2026-09-19: the kind and its baseline, the column, the initial state, the deploy, the badge and both filters. Run end to end on a stand 2026-09-20 — deployed, a document of its own, the card and the index open, the badge and the filter draw. Not built: transitions, and a screen over the set — an enum has none either, a set is read through the columns pointing at it.

- **What separates it from `enum` is the transitions, not the colour.** An enum already HAS `Order` — the position in the file, deployed as a column — so on the shape side the difference is two columns, and only one of them is drawn. What pays for a kind is behaviour on the REFERENCING side: once transitions exist, a picker offering every value is a lie. The kind also buys the one thing a key on `enum` could not: a json schema whose text teaches the concept to whoever writes the file.
- **The kind says what the rows are, the column type says what the reference has.** `EndpointKind.State` — these rows carry colour, roles and later transitions; `ColumnType.State` — this reference has a lifecycle. A column must say what it is instead of sending every reader through `RefTable.Storage.Kind`, and the load then checks the two agree: a state column whose target is not a state set fails there. The check came out as a table — the kind a type requires, and the address to suggest, one entry per type — so `enum` and `account` are asked by the same line; the enum half had never been asked at all, and reached the database as a foreign key that could not hold.
- **No `TableTrait.Stateful`.** A column of that type is the whole answer to "does this have a lifecycle", as `ColumnType.Autonum` answers "is this numbered" and a non-empty `printForms` answers "does this print" — the trait that used to answer the last one was deleted for exactly this. A trait would also have to ADD the column, and the platform adds columns only where it reads and writes them itself.
- **The colour is the dictionary that already exists.** `ColumnType.Color` and the tags' vocabulary, checked at load against `TagLabelStyle` — the list that matches the CSS, so an accepted name always renders. The CSS side is one list now (`Palette.less`, ISSUES 3.12; the picker and `CardStyle` still apart), and collapsing the rest can only narrow the check. The vocabulary grows through it: `White` was added for the row below, in the enum and in the CSS together, because a name in one of the two is the invariant broken.
- **The 'All' row is white, and a state with no colour is not.** The filter draws that row with the same picker as the rest, and one with no colour draws as nothing at all — white on white, which reads as a control that failed rather than as 'no filter'. So the platform gives it one, out of the same vocabulary the load checks against: what the deploy writes stays a row an author could have written. A declared state with no colour keeps none — that one is a choice, and it draws as a plain label. Price, and it is the seed-blind class (Seed): the colour is a constant of the generator and not a declaration, so it never enters the seed and reaches a deployed database only when something else moves the hash — the platform's Build, or any edit to the values.
- **A value's role is a closed set of four, and the cardinalities are the design.** `Initial`, `InProgress`, `Success`, `Failure`: exactly one `Initial`, exactly one `Success`, any number of the other two, counted over the living values — a void `Initial` beside a live one is a migration, not an error. Success is measured, so it is single — "did it get there" stays one comparison and conversion falls out of the set. Failure is classified, so it is plural — no budget, duplicate, won't fix are reasons, not outcomes. The price: a lifecycle with two good endings picks one and tells the rest apart by another field.
- **The column is `Role`, and the four are words.** Not `StateType`: `Type` says nothing, `Kind` is taken, and `Role` fits all four readings where `Phase` breaks on the endings. Not `I/P/S/F` either — the column lives on a table of five rows, so shortening it buys bytes that do not exist and costs a second dictionary between the file, the database and the generated predicate. `InProgress` and not `Processing` for the same kind of reason: three nouns and one -ing participle read as "something is processing this record", and two words joined are already a member here (`AccountType.OffBalance`).
- **That role answers what a separate flag would have.** Terminal is `Success`/`Failure`; "open" is `Initial`/`InProgress`, emitted as a predicate and never as a `Closed` column, which would be a second `Done`. The starting value stops being the endpoint's business too: an `initials` entry on a state column is a second spelling of `Initial` and is refused at load — `fixed` with it, since a fixed field IS the initial of a new record.
- **What is written in the file is what is stored, because nothing translates it.** `role` is spelled as the member of `StateRole` — that very string lands in the column and in a generated `exists` — and `color` in lower case, because that one lands in a CSS class, where case decides whether anything is painted. Two registers in one row, and the rule that sets both is whether the spelling survives the load: `columnType`, `trait`, `postDirection` die at deserialization and are camelCase like the keys; a value the platform keeps is written as it will be kept.
- **The model of a set is composed, and that is not decoration.** `/state/order` gives `OrderState`, not `Order`: the candidates arrive as an array in the ROOT of the page that shows the record, where `Orders` is already the records themselves — one name for two arrays, one `TROrder` for two types in one `.d.ts`, `@[Order.packed]` over the document's own keys, all silent. A set of states is always named after something that has a screen; an enum escapes this by being named after a concept (`vatrate`).
- **The SQL schema is `state`, written out.** The convention shortens long words — `catalog`, `document`, `journal` — and `state` is already short; `enm` is the odd one out, not the rule. Written into `ToSqlSchema` all the same rather than left to its fall-through: falling through means "this string is already a SQL schema name", so only a line there says the word was chosen. `case` will need one for a harder reason — it is reserved in T-SQL.
- **Two filters on one column, and the second is a kind of its own.** `State` compares the code on this table; `StateRole` asks the SET (`exists`), which is another table, and by the rule in Filters that makes it `FilterKind.Role` rather than a mode. Its candidates are the only ones that are not data — four members of a platform enum, written out with their `All`, since there is no deploy here to add that row. Named after the column, so two state columns give four entries that cannot meet. What this does NOT give is "open": that is two roles, not one, so it takes either a multi-select or a two-valued entry of its own. Deferred until a screen asks, and it is this filter's question wherever it is asked — not a kind's: `case` was written down as its owner and is not one, since the column it would ask about is the author's.
- **The default panel shows one of the two.** Both are in the namespace, and the default form names only the states: two questions about one field, side by side on every screen that never asked for either, is a panel nobody designed. Hiding is the one thing a form may do to a filter, so the entry costs nothing while it waits — a declared form names `{Column}Role` the day a screen wants it. The CollectionView and the index SQL still carry it, as they carry every filter of the namespace: they never go through a form.
- **The initial state is resolved where the SQL is written, never in the bake.** The same line the `inherit` rules are cut along: the far half of a reference is linked after publication, and the code `Initial` is the far half. `MetadataExtensions.AllInitials` is one answer for the two readers that need it — the defaults recordset, which sends the values, and the map, which resolves the references among them. The document's operation moved in there with it and stopped being spelled twice, in two different ways.
- **The column stays nullable, and the NOT NULL that was designed is refused.** It would have to come from a default, and the only one available is the set's `Initial` — a value derived from another endpoint's DATA, which then enters the seed, where it is compared, and which no `create table` can follow once it changes. Every path of the platform fills the column; an insert that bypasses the platform leaves null, exactly as for any other reference.
- **A transition is a verb the platform declares, not a procedure an application names.** Changing data without posting is not expressible today and the verb list grows by decision (see Commands), so transitions arrive as the second verb beside `post`. That is also what decides whether one table may carry two state columns: it may, exactly when the command names its column.

## Colour: a property of the row, never of the reference

A row whose table carries a column of `ColumnType.Color` draws as a badge in that colour — on its own name in its own index, and wherever anything references it. Nothing is declared on the referring side, and no column type says "draw me": the colour travels with every resolve because the target's shape has it. Decided 2026-09-20, built the same day.

- **Asked of the SHAPE, never of the kind.** `TableMetadata.ColorColumn` is the one answer, read by the SQL that sends the colour (`SqlBuilder.RefFields`, in the reference map and in a set's candidate list alike) and by the grid that draws it. A state answers yes because its baseline holds the column, a catalog because the author wrote one — so the `ColumnType.State` branch in the index grid is gone, both roads arriving at one badge. `RefFields` is the old `StateFields` with its two halves separated: the colour by shape, `Role` still the state's own, since a role is not drawing.
- **The TS type already promised it.** `TsProperties` walks the target's own columns, so `TItemCategory.Color` was declared while the map sent Id and Name and nothing else. The rule narrows that gap rather than opening one — the direction of the old note under `StateFields`, now general.
- **Price, and there is no opt-out.** Every reference to a table with a colour draws as a badge, everywhere. "Just the name here" has no spelling; the answer is not to declare the colour column. Accepted, because a colour is declared in order to be seen.
- **Two colour columns are not an answer.** Which of them is the ROW's colour would be a guess, so neither is: nothing is painted and each draws as an ordinary column. In `ColorColumn` and not at the three readers, so they cannot drift on what "has a colour" means.
- **The colour paints the NAME, and then it is not a column of its own.** `green` beside a green name is one fact written twice — the same act as the tags splice, which is why both go through one `NameContent`. A colour column that paints nothing (no name to paint, or two of them) is shown and draws ITSELF: style and text are the one value.
- **`ColumnType.Color` is a style from the platform's vocabulary, not the colour of a thing.** The value lands in `:class`, so "морська хвиля" as a product's colour finds no class and renders an unpainted badge — that column is a `string`. Nothing checks an author column against the vocabulary; what holds it there is the `ColorPicker`, now the control for the type in a card and in a collection row (it is the one the tags dialog has always used — a branch, not a new control).
- **Nothing referenced, nothing drawn.** The badge binds `If` to the reference's `Id`: an empty reference rendered an empty badge, and a frame around no text reads as a control that failed rather than as a blank cell. By `Id`, because that is what "the reference holds a row" means — a name may legitimately be empty.
- **A selector is painted too, by the same rule.** Not as a badge: its closed value is the text of the search input. The `ComboBox` style (a `<span>` value) was refused - it loses choosing by typing, which is how a catalog is picked; a badge over the field out of focus is a rewrite of the control. `ColorProperty = ColorColumn?.Name` on every selector whose target has one (card, row, index filter); the client puts `color color-<value>` on the value for the chosen element (the `input`, the combo's `.selector-combo`) and on each row of the list for its own (`colorOf`) - not on the control as a whole: the colour is the row's. Not on the input group either: its border belongs to the control's states (focus, invalid), and the list inside it would inherit. The first consumer of the palette as CSS variables (`themes/tabbed/Palette.less`: `.color-<name>` puts `--color`, the values are the schemes' `--clr-*`): the value and each row of the list are written in the hue inside a frame of it, an outline badge (`.palette-outline`); a filled row was tried and rejected on sight. The other copies move there step by step (ISSUES 3.12). The `hyperlink` style keeps its link colour - its rule is more specific. Null - no colour column, or two - writes nothing. The element carries the column on every road: the map and the candidates (`RefFields`), the fetch and its maps (`ColorField` - apart from `RefFields`, since the fetch reads the table itself and not the reference view). Not reached: a report filter's selector. 2026-10-04.
- **What this does NOT give is the picker.** The candidates still do not ride with the page, so choosing stays a selector with no colour in it. That remains one declaration away and is deferred: a type meaning "the candidates arrive with the record, the choice is made in place" — `pick` is the word, and the colour is no longer part of what it would say.

## Cases: the lifecycle the user owns

`/case/<name>` — a record that is opened, worked and closed: a task, a deal, a lead, a ticket. Decided 2026-09-18, not built — [ISSUES 3.13](ISSUES.md).

- **Not a document without `post`.** A document asserts a moment: binary lifecycle owned by the platform (`begin tran` → `update Done` → `exec`), read-only once posted, and its `Date` is data the user sets. A case lives through time — many declared states moved by the user, projecting into nothing, editable to the end, and its birth is a stamp rather than a field. Modelled as a document it gets two creation dates with the editable one meaningless, a period filter forced by the kind, a read-only axis hanging off `Done`, and a command set derived for posting.
- **The baseline follows from that:** `Id`, `Void`, `rv`, `Name` (a case has a title where a document has a number), `Memo`, stamps. No `Date`, no `Done`, no posting stamps, no period.
- **The price of having no `Date`: a case shows no date at all.** Stamps are out of `IsIndexColumn` and `IsEditColumn`, and the member lists are built from those, so `UtcDateCreated` is neither a grid column, nor a name a form may write, nor a sort a header offers; the period filter is hardwired to `a.[Date]` besides. Whatever date a screen needs — opened, due — the author declares as an ordinary column.
- **The state column is the author's, and the kind does not require one.** Revised 2026-09-20; it used to be "exactly one, required", checked at load. The platform adds a column only where it writes and reads that column itself, and a case's state is written by the user's own save. Nothing reads it by name either: the initial value is the set's answer, and the transition verb will name its column. So it is declared like any other reference and found by type, as `autonum` is; requiring it would be a guard ahead of its user, and would cost a second file (`/state/<x>` with its values) before the first screen opens. A case declared without a state degrades into a catalog edited on a page — visible on the first screen, silent nowhere. What makes the kind a kind is who owns the lifecycle, not a check.
- **"Open" is a filter the form shows, and nothing is written into the index SQL.** Revised 2026-09-20; the plan used to emit the predicate literally. Which records are open is the role filter every state column already contributes (`{Column}Role`, an `exists` on the set); it is merely unshown, because the default panel shows the states and the role waits for a form that names it (see States). A literal predicate has no parameter, so there is no control to clear it, it rides `browse` and `indexpartial` with the index, and the fragment search runs under it — a closed case is not findable by its title, with the reason stated nowhere. The kind cannot name that filter in a default form either: the column is the author's, and the kind knows neither which one it is nor whether there is one. A `Closed` bit stays refused — it would be a second `Done`. That "open" is two roles and not one belongs to the role filter, not here.
- **The assignee is not in the baseline.** The platform does not read it, and a second `User` column — a watcher, an approver — would turn finding it by type into a guess. An ordinary declared reference, and "my cases" is a filter when it is wanted.

## Registers: what holds over an interval, written as two rows

`/register/<name>`, schema `reg` — the third member of the family a posting writes into, beside `journal` and `ledger`. Its row is not a measure but an assertion in force from a date: hired 01.01, dismissed from that post 20.07; an allowance granted and cancelled. The question is "what is in force at D", never "how much". Decided 2026-09-19, not built — [ISSUES 3.14](ISSUES.md).

- **A kind, because a kind's baseline is what the platform writes and reads BY NAME.** Compared with `journal` it looked like none was needed — a journal's baseline is `Id` and `Date`, it knows nothing about its own columns. The right comparison is `ledger`, whose baseline is dt/ct/acc/sum, "what `post` writes from its own keys". Here it is the direction and the pair. Many simple kinds over one kind with modes: a kind is a dispatch and widens nothing shared.
- **Two rows, not one row with From/To**, because the closing act belongs to ANOTHER document. One row would mean a dismissal editing the row a hiring wrote, and every unpost here is a derived delete — undoing that would need an undo-update, which does not exist. With two, the minus dies with its own document and the interval reopens, for free.
- **The pair is the origin of the opening event, `(DocumentType, Document, Row)`.** Not the key tuple: two allowances of one type are indistinguishable by it, and exactly one of them is being cancelled. Not the journal row's Id: posting rewrites those rows, so it is unstable across a repost, while documents are never rewritten.
- **`ColumnType.Document`/`Row` always mean "who wrote this row"; the pair rides a column of its own.** Unpost deletes by provenance, so putting the origin there breaks both ways — the closing document never finds its own row, and unposting the opening one deletes a row it does not own, leaving a document `Done` with no movements. `ColumnType.Row` cannot carry it either: that one looks back at my own document, the pair looks sideways at another's.
- **`Link` is empty on the opening row, and the attributes live only there.** One decision read twice: the state at a date is then an anti-join and the attributes come off the opening row with no join at all, while attributes repeated on the closing row would be a second version of the truth. Two filtered unique indexes carry the rest — one opening per document row, one closing per fact.
- **Unposting a document whose facts someone else closed is refused.** `DbRemove`'s referrer question asked of the other verb: unpost is the deletion of effects, and effects that others leaned on are not deletable. Derived rather than declared — the registers a document writes are named in its own `post`. Cascade is refused: a document silently unposting another is ambient authority.

A slice register — one value per key, superseded implicitly, read as "the last row ≤ D" — is a separate kind and deliberately unnamed until it is built. Two structural reasons, both in ISSUES 3.14: its rows are also entered by hand, and its key is declared by the author rather than owned by the platform.

## Links: part and belonging, and one naming rule

Two relations wore one word. A details row and a tag entry are **part of** the record they hang under: platform-emitted, dead when it dies, never shown, no target of their own. A subordinate catalog record **belongs to** an entity: own save, own card, referenceable, several such links per table, each with a declared target. `Owner` named the first and was the right word for the second. Decided 2026-09.

- **`Master` is the part, `Owner` the belonging.** They share "a link to a parent" and nothing else: opposite lifecycle (one dies with the record, one outlives it because documents point at it), opposite data path (one is loaded and saved inside the master's model, one saves itself), FK target derived in one case and declared in the other. One type would mean "target derived OR declared depending on where the table sits" — the "where do I read this from" question again.
- **Told apart by shape, not by remembering which word is which.** `Master` carries no `target` (only `SqlDbGenerator.DeployTables` knows what it points at); `Owner` requires one. One field answers it while reading any file.
- **The rename was total — the whole reason it was done now.** A half-rename leaves one word with two meanings, exactly what was being removed: `Constants.FieldNames.Owner` is gone, tag entries included, and `Owner` is the belonging and nothing else. Nothing is deployed on this layer yet, so the cost was zero; the same rename after the first installed base is a migration for everyone. The word goes to belonging because that is 1C's «Владелец», and a migration is the only reason any of this is being built.
- **A link column is named for what it POINTS AT.** `[Document]` on a waybill's rows, `[Agent]` on an agent's tag entries, `[Agent]` on a ref — one rule for every link instead of "refs by target, this one by relation". The name stops being a marker, so `PostStatements` and `RefMapBuilder`, which spelled it literally, now find the column **by its type**, as the platform does everywhere else.
- **`MasterField` is held, not derived; exactly two factories write it.** The hanging table alone does not know its master, so the name is set where the master is in hand — `SetDetailDefaults` and `CreateTagEntriesTable`, beside the `Table` built from the same `Model`. An empty string is a real answer: hangs under nobody. Price, paid knowingly: the tag SQL spells `Table.Model` at the reader sites rather than asking the entries table — the trade `TagEntriesTableName(Table.Model)` already makes one line above.
- **`master` cannot be declared in a file**, and is not in the json schema's `ColumnType` enum: the platform emits this column, and an author reaching for the word gets a schema error instead of a silent second column. `owner` is declared like any reference.

## Owner: the picker filters, the save holds

A reference to an owned record picks among those whose owner is the value of the matching field beside it — a contract by the document's agent. Built 2026-09-29 (skill: `metadata.md` → `Owner`).

- **One behaviour, and it lives on the REFERENCING side.** Filter on the picker, check on the save. The owner itself is an ordinary nullable reference, editable: consistency is held by who points at the record, so correcting a contract entered under the wrong agent stays possible. The immutability and the "shown while new" form rule designed earlier are dropped — both guarded the owner, and the owner needs no guard.
- **`Company` is an owner with a fixed target.** Same filter, same check; the counter and `{p}` are its extra. So `OwnerLinks` reads both types, and the company catalog's references get the filter for free.
- **The field is found, not declared.** `MetadataExtensions.OwnerLinks`: Company by TYPE (a second reference to the company catalog is not the record's company), Owner by TARGET compared as the table (a second address over the same catalog still holds the owner). Where the reference sits first, then the header — a contract in a row is picked by the document's agent. None is no filter; two are a guess and throw. Resolved where SQL and screens are written, never in the bake: the owner columns are the far half.
- **Two roads to the candidates, one query.** The template gives the record a `$<Ref>Owners` property — `{ Agent: this.Agent.$id }`, `this.$root.<Model>` for a header owner — bound to the selector's `Data`, which the browse turns into its url (the index already filters on any reference) and the fetch receives as arguments (`SqlBuilder.FetchOwners` reads owner columns only). The id and not the element: the fetch reads JSON, where an element arrives whole. An empty id is no filter on both roads.
- **The check runs over what was SENT, before the merge** (`SqlBuilder.OwnerCheck`): the picker is the browser's half. A record owned by someone else fails, and one owned by nobody too; an empty field checks nothing, as it filtered nothing. One message, `UI:@[Error.Owner]`, the application's to translate.
- **Not built: the page of an owner** — its subordinates as tabs (`show` in the skill). A tab is the index of another endpoint filtered by this record, which the index already does by url.

## Birth on basis: the source offers, the url names the source, the load reads variables

A document created from another: the menu 'create on basis' on the source, and a new record filled from it. Built 2026-09-30 (skill: `metadata.md` → `BasedOn`, «`basedOn`»; design and rejected: a2v10-md-skill `concepts/basedon`).

- **`ColumnType.BasedOn` is a reference whose target must be a document** (`TargetOf`). The type picks the kind of target, not a table: documents live in several (`Orders`, `StockDocuments`). In a header it is set by birth and by nothing else, so the card draws the document as a link (`ControlsXaml.DocumentHyperlink`, shared with the grid cell), no picker; in a row it is picked - an allocation. Not `Document`: that is a journal's provenance, written by posting.
- **Declared on the SOURCE, in the document's own file** (`DeclarationMetadata.BasedOn`). The command is read off the file of the screen it shows on, as `ShowTrans` off `post` - no registry, no fact from another file. Not in an operation file: the menu is built once per screen, and in a grid the row it acts on is not known when it is. A list, the order is the menu's; a target is offered once. `operation` follows `?Op=`: written exactly when the target lists operations.
- **Phase 2 checks only in the direction the file points** (`ResolveBasedOnAsync`): the target is a document, its operation, the pair, what is copied (`BasedOnMapping.CheckDocument`, `.Rows`). The field the basis lands in is NOT looked up there - that is a search in another endpoint's header for a column pointing back, and the two documents usually point at each other, mid-load in one walk. The target finds it at birth, in its own header.
- **The url names the source: `new?BasedOn=<id>&Base=<path>`.** Ids are per table, so one number does not say where to read; reading the row's operation first was a round trip to learn what the command already knew. `Base` gives the source endpoint, its `basedOn` entry for this target, its table. PascalCase keys (`Constants.FieldNames`), as `Op`.
- **The copy is one law asked twice** (`BasedOnMapping.SourceOf`): at the source's load, which refuses a file that cannot be copied, and at birth, which writes it. Author columns on both sides (`Columns`, never baseline); the number, the operation and the row kind are issued, not copied; `document` holds the deviations; the rest by name and domain, and a name meeting another domain is passed over - nothing in the file could exclude it, and the card shows the gap. Rows from the source's collection of the same name into the target's kinds named in `each`.
- **Birth fills table variables of the TARGET's shape, then the stored load reads them** (`LoadRows`: the table and the key a load reads from - `Stored` is the tables and `@Id`). Recordsets, the map, the defaults come out of the same text as for any record; nothing past the fill knows the record is new. The map has to read the variables and not the source: an inherited reference (`VatRate` from `Item`) exists only there. One variable per table of the document, a collection not copied stays empty - every reader of rows reads them all.
- **The record's key is the base's Empty** (`AppPlatformId.Empty`: `0`, the zero guid): non-null, so the rows hang under it (`ParentId`); empty, so the client and the save take it for new. The rows' keys are null.
- **Initial values are NOT written by the fill**; a column that has one is left null where the source gave nothing, and `$Defaults` fills it: A2v10.Data applies defaults to an object with an empty key, into its empty fields only. Written by the fill, `today` bypassed `!!Utc` and a document born between midnight and the UTC offset took yesterday's date. Order: source, inherit (an `update` of the variables, into empty fields), defaults.
- **Not built:** the menu grouped by category (a static `DropDownMenu` has no headers, `DropDownMegaMenu` groups only over `ItemsSource`); the journal of execution; the rest of the source instead of its rows.

## Two files in one folder: data from the shape, screen from model.json

A folder may hold both. `metadata.json` owns the data: SQL, deploy, commands. `model.json` owns the screen: `view`, `template`, and everything it always could (roles, permissions, popups). The split follows the seam the builder already has - `LoadModelAsync` and `RenderPageAsync` are two halves - and the unit is the ACTION: `index` on a procedure and `edit` on the metadata layer, both over the one table the shape deploys. Decided 2026-09.

- **The switch is a value of `model`, not a key beside it.** `model` already answers "where do the data come from" three ways - `""` (a screen with no model), a name (procedures), `$sql:key` (a text) - and `$meta` is the fourth, in the same slot. `$` is the platform's mark on a value that is not a name (`$sql:` was `@sql:` until now; no file used it). It inherits as `model` always has: `$meta` on the root and a name on one action ejects that action; a name on the root and `$meta` on one action is the same sentence the other way round. A root `$meta` with no actions at all is a legitimate file - it is there for roles, permissions or popups. The old `meta` key is gone: it carried an ADDRESS in SQL names (`schema: "cat"`, `table: "Agents"`) from the time metadata was read out of the database, and the layer moved to files addressed by folder without it.
- **The endpoint's identity is the folder, and the file never repeats it.** The address is `platformUrl.LocalPath`, the same two segments `metadata.json` is found by; a `$meta` written deeper than two is refused by `ParsePath`, not truncated - the only new way into that check is a key a human wrote.
- **`view` and `template` are taken one by one:** written, the file; absent, generated. Not "both or neither" - a hand-written template under a generated view is exactly the cheap case.
- **Price, named and accepted.** A hand-written view binds by string and loses the load-time check `forms` has: a renamed field renders empty, as a print layout does. A hand-written template loses the RULES - required, computed, inherit, totals, tab state are compiled into the generated one, and a rule added later never reaches the hand-written copy. That is why the default must be obtainable as text (ISSUES 3.6), for templates as much as forms: "write it by hand" means "start from what the platform wrote".
- **`model.json` is the box's hatch, and it is visible as one.** Its `commands` name procedures freely; the metadata form cannot reference them, a hand-written view can. The boundary that used to run inside one mechanism now runs between two files, so which file you are in says whether the beam covers you.
- **What this retires: eject-as-sources.** Generating `model.json`/ts/vxaml only pays if the SQL is ejected too, as procedures - and the layer writes none. Two files make screen customization independent of that, so the SQL eject is deferred rather than owed.
- **The default is obtained as text by `a2 meta materialize <endpoint> <action> view|template`** (`EndpointMaterializer`). One thing per call, because the two cost differently to own. What is written is what the runtime renders - the same builders, types printed. It never overwrites a file a human owns; the one file it rewrites every time is the `.d.ts` map, a compile target of the shape. `model.json` is not edited: the fragment that points at the file comes back in the result, and the author merges it. `browse` has no template of its own - it runs the index one and its map imports `./index` - so `browse template` is refused with the line to write instead. The form-JSON rung (`meta form`, ISSUES 3.6) is not built.
- **Generated output is checked only where something reads it back.** The first materialize found what runtime rendering had hidden for months: the `.d.ts` without the default columns (`TsProperties` walked the declared ones), and a xaml writer emitting `Rows=""` and losing `Bind.Format`. Types erased at run time and xaml never re-read cost nothing until a reader appeared (2026-09-16).

## Names: what every place a name lands in accepts

A name from a file — `schema`, `table`, `model`, `fields`, `details` keys and their `kinds` — is letters, digits and `_`, not starting with a digit. Refused at load (`CheckNames`, after `SetDefaults`). Decided 2026-09.

- **A whitelist, not a ban on `$`.** SQL brackets the name; a TS type, a model member and a binding path do not; `.` and `!` are data-model metacharacters, `]` breaks the brackets. Banning one character left the rest open.
- **`$` is why it exists.** It separates what the platform adds (`cat.[Agent$TagEntries]`); an author name holding one could spell that table, and two `CREATE TABLE`s would collapse silently.
- **Letters of any script.** A JS identifier allows them, and SQL quotes them.
- **A row set's table is `<owner model><key>`, and no key writes it** (`SetDetailDefaults`; `table` is not in the schema's `details`). A row set is not addressable on its own - no endpoint, folder or file - and the platform names it as it names its type, collection and TVP. A `table` key there was overwritten silently, which a schema cannot catch: it checks that a key is present, not what is done with it.
- **The platform's own names live under `$`.** Its tables are built in code and never pass the check; an alias inside generated SQL takes `$` too (`[$Kind]`), so no author name can meet it.

## Stamps: typed by what a walk asks, written by name

Who + when on every record the user keeps: creation and modification on a catalog, a document, folders and tags; posting on a document. Not on details, tag entries, journals — a part's record carries the stamp, a journal is rewritten by posting. Decided 2026-09.

- **Four types, because nullability is a type's answer.** A type answers what a walk over columns asks: SQL type, FK, nullability (`DeployNullable`), whether the client sends it. The posting stamp differs in nullability alone, hence `StampUserNull` / `StampDateNull`. WHICH stamp a column is stays its name: every statement writing one names it, as posting names `Done`, so no walk dispatches on it.
- **Never sent.** Out of the table type and the DataTable by one predicate (`IsSentColumn`), whose column order must match. Written by the merge (insert: both stamps; `when matched`: modification), by Void, by post; unpost empties the posting stamp — nothing of a posting is left behind it.
- **A default is what makes a stamp not null** (`0`, `getutcdate()`). `DeployNullable` reads `DeployDefault`, and `CreateTable` writes the same expression — one road to NOT NULL, the same a domain's zero takes ("NOT NULL: the domain's zero").
- **'Who' is bigint, FK on `a2security.Users(Id)`** — and so is `ColumnType.User`: a login is keyed bigint whatever base the application rests on.
- **The system user (Id 0) is seeded by the application deploy, before the keys.** Not by the platform script: its administrator seed is guarded by "the table is empty", which an earlier row would turn off silently.
- **Not history.** A stamp names the author of the current state. `TableTrait.Audit` is to mean the change history (a `$History` table and a trigger); not built.

## Logins: a view to resolve by, a module to choose in

`ColumnType.User` is a login — `a2security.Users` and nothing more: no position, no phone, no department, and none of them arriving later. What the platform owes such a column is one thing, reference resolution; the screens over logins are the admin module's and already exist. Decided 2026-09-20, not built — [ISSUES 6.5](ISSUES.md).

- **A login is one entity, a person is another, and the second belongs to the application.** `Manager`, `Assignee`: the author writes `user` or a `ref` onto a catalog of employees, and nothing asks which — both are references, one selector, one resolve, `Manager.Name` either way. One question decides it: does the domain hold a person with no login. If it does, that catalog carries a **nullable** `user` column, and the nullability is the whole reason the second shape exists; the link runs employee → login and never back, because `a2security` is not ours to widen. In doubt the asymmetry decides: `user` → catalog is bigint → platformid across every document that already stores one, and the reverse is never needed.
- **Only the resolution is ours.** `A2v10.Module.Admin/userrole/user` already carries index, edit, create and invite — a system endpoint of our own would be a second list of logins standing beside it. So no builder and no generated screen: what is left of the shape is three facts (the view, `Presentation`, `RefTypeName`) plus `Path`, the module page's URL, a constant of the platform and never a string an author writes.
- **That is also what removes a third key domain.** `@map` declares its column from the type of the REFERENCING column (bigint) and the resolve emits `[Id!!Id] = a.Id`, so nothing walks the target's own `Id` — and `ColumnType.Id`, which means platformid, never has to stand over a bigint key. A `browse` of our own would have walked it, and the address would have cost a third domain beside `Id` and `NaturalKey`.
- **The view resolves, it does not offer.** Two row sets, and only the first is the platform's: resolution returns everyone ever stored — blocked, dismissed, and the system user Id 0 — or last year's document opens with an empty `Manager` and a stamp draws nothing. Whom one may pick now is the screen's filter. The same sentence a set already makes with `void`: a withdrawn value stops being a candidate and keeps resolving. `a2security.ViewUsers` is the admin's own and hides Id 0, so this is a second view, with the narrowest contract there is — `Id` bigint, a display name, all rows.
- **Its schema is `a2security`, and the platform script deploys it.** A view is an assertion about `a2security.Users` and moves when that table moves, so it lives where its truth is kept. Not `a2meta`: that answers what the deploy knows about the APPLICATION's schema, and a login is not part of it. Not `usr`: that is the application's seam — `usr.GetProfilePreferences` is an unverified promise the application fulfills — and a view without which every `user` column breaks cannot sit where an application may forget it. Not a new word for something that already has two. `a2 deploy` cannot write it either: the metadata deploy writes what files declare, and this has to exist before the first one runs.
- **The admin module is a dependency of the scaffold, written down and not checked.** A `ProjectReference` plus one line in the template. It brings `adm.*` along, which is the right way round: an application on this layer needs the administration anyway, and the `user` column merely uses what is there. No check at load that the module is installed — a guard designed before its first case; without it the picker fails on the first click, visibly, while the resolve still works because the view ships with the platform.
- **'The current user' lands in `InitialSource.Context`, beside `today`.** The one place the two shapes are not symmetric: on `user` the value is `@UserId`, which every statement already receives; on a catalog of employees it is the profile road that exists (`usr.GetProfilePreferences`, `platformid`), with the procedure written by the application. Deferred until the first screen asks for "assigned to me" — then it is one word.
- **`company` was decided apart** (2026-09-29, "Owner"): an owner with a fixed target, a catalog with a shape. It shared with `user` only the symptom in ISSUES 6.5.

## Seed: what the database is told about itself

`a2meta.Tables` / `a2meta.Columns` are the deploy's own picture of the schema, and the referrer set is read from there rather than from metadata — in release there is no `AllElementsMetadata` walk, so SQL is the only thing that can answer a question about the whole application. Decided 2026-09.

- **A fact enters the seed only when SQL must answer it for the whole application at once.** Referrers and the part-of edge (`master_schema`/`master_table`/`master_column`) qualify; `kind`, `traits`, `model` do not. Without the line the seed drifts into a copy of the files.
- **The edge comes from the walk that builds the foreign keys** (`SqlDbGenerator.DeployTables`), so seed and DDL cannot disagree about what hangs under what. Written only where a link column exists: the walk hands a master to the autonum counters too, and those are keyed by a code with no link at all.
- **It answers "used" correctly for hanging tables.** A details row has no `Void`; the record is the master, so `DbRemove` joins to it. A row of a voided document stops holding what it points at.
- **What a generator branches on and the seed does not carry, the hash cannot see** — the seed-blind class. Turning on a trait or changing a kind deploys nothing unless it moves the seed; `$TagEntries` is in the seed for that (2026-08-27). Hashing the whole script was refused: three of its generators follow the file system's order, and a moved folder would redeploy.
- **The referrer set is a cache of the database, dropped with the file caches** (`ClearAll`). The deploy that moves it runs on the request after the reset (`_metadataDirty` is set in the same block), so the first `DbRemove` after a deploy reads it fresh. Two triggers that must coincide are stated, not assumed: a stale set permits voiding a referenced row, the soft delete trips no foreign key.
- **`SyncSchema` adds columns and nothing else** (`a2v10_metadata.sql`, from `a2meta.Columns`). A new field reaches an existing table; a changed type or a dropped column does not, and such a table is dropped by hand.
- **Read with a left join, never inner.** A missing `Tables` row must not DROP a referrer — that is a permitted delete of something already referenced. `GetFkReferrers` aliases its columns to the property names of `TableReferrer`: the list loader matches ordinally, so a lower-case one fills nothing and the row arrives empty instead of failing.

## JSON schemas: one original, copies by build

The schemas of `metadata.json` are the format's teaching text, so where they are edited matters. Decided 2026-09-20/28.

- **The original is `Platform/A2v10.App.Assets2026/Application/@schemas`.** An application's `@schemas` is build output, copied from the RESTORED PACKAGE (`CopyAssetsToProject`): an edit there is overwritten by the next build, and an edit of the original reaches an application with the package version. A copy one version behind is the normal gap, not drift. The stand copies from this tree (`MainApp.csproj`); `sync-json-schemas.cmd` is the same copy without a build.
- **A schema another file references by a relative `$ref` carries no `$id`.** An absolute `$id` resolves the reference against its URI, and the editor goes to the network for a file that is not there. Definitions are referenced, never copied: two copies of `fields` or `form` part on the next edit.
- **One spelling per enum, camelCase.** The loader parses enums case-insensitively, so the schema is the only place a spelling is held.

## Validation: the endpoint assembled, never the file parsed

`EndpointValidator` builds everything the layer can produce for one endpoint and throws the text away; what it reports is what threw. The beam of #1 at the assembly seam, so the unit is the assembled result and not the declaration. Decided and built 2026-09-20. The CLI leaf it is reached through: [Tools/A2v10.Cli/CLAUDE.md](../../Tools/A2v10.Cli/CLAUDE.md).

- **The unit is the ENDPOINT, never `metadata.json`.** A declaration layers over its `storage`, carries `seed`, and points at `/autonum` and `/state/<name>` — all checked at load, all in other files. A check named after the file would promise one file and read four. It is also why the address, not a path, is what the leaf takes.
- **A validate that stops at the bake declares healthy a page that throws on opening.** That is the `ColumnType.Operation` case exactly: the declaration was legal and the generated index met an ambiguity nothing had asked it about. So the stages are the artifacts — the bake, then the screens (XAML, template, `.d.ts`, every action), then the print models (the `Model` of every declared blank).
- **Stages are chained and stopped at the first throw**: for a data endpoint `declaration → screen → print`. The order is dependency and nothing else — there is no screen without a declaration and no blank without a screen. One error per run is not a limitation being tolerated: the generators throw rather than accumulate, and teaching `Bake` to accumulate is a rewrite of the one walk every kind goes through. A model fixing one thing against a fast loop beats a list it applies half of.
- **The STAGE SET is a property of the endpoint's type, and the load is what establishes it.** So the map is filled in two breaths: `declaration` alone first, the rest once the type is known — a load that fails names no further stages, because what this address is, is exactly what was not established. A hardcoded three ran the guard of `GetNormalEndpointAsync` as if it were a finding, and a report read as broken while two stages it does not have read as unreached (2026-09-20). The dispatch is a SECOND one, beside `ModelBuilderFactory`'s, and it is not a slip: every member of `IModelBuilder` is an action against data, so the runtime's seam cannot answer "what assembles without a database". Its cost is paid at the default arm — a type nobody taught this tool brings no stages at all, which reads as "nothing was checked" and never as consent.
- **A report is checked by building its page, and that is three refusals deep.** The type names a builder (`BaseReportBuilder.Create`, the one place a report type means anything — the validator must never own a second copy of that switch), a ledger report over a non-ledger surface is refused by the builder's own constructor, and every declared filter, group and data column resolves against the surface. Built with NO parameters, which is the first open: a report is drawn before it is run, so its own defaults are what the page must survive. Not serialized to XAML afterwards, unlike a generated screen — nothing ever writes a report page as text, so serializing here would exercise a road that does not exist. No `print` stage: a report prints the page it rendered and declares no blank.
- **Nothing is parsed, ever.** Not the generated SQL — if that is malformed the generator is broken, which is what tests are for. Not the author text spliced into it (`computed`, `visible`, filter expressions), which is the one class no build can catch: it is verified by executing it, and there is no offline substitute worth a dependency. `ScriptDom` and `SET PARSEONLY` were both weighed and refused.
- **There is no `sql` stage.** It cost the most — the builders are `internal`, so it needs public ports — and bought the least: generating a statement and seeing the generator not throw is strictly weaker than running it. Named consequence, on the record: the SAVE generator now has no beam at all. Executing does not reach it either, because saving writes data. It is caught by the first save on a stand, and that is the whole guarantee.
- **`print` is last although it is the only one with no other beam.** A broken screen is seen by opening the page; a broken blank is seen by nobody until someone prints — the layout is never read, so a cell over a field `Model` does not carry renders empty and says nothing. Last only because it depends on the screen; were it free to move, it would go first.
- **The screens are the BAKED FORMS, not a list of actions.** A shape nothing renders — a set, a numbering — has none, so the stage passes with nothing built; the same sentence that refuses to call the missing `browse` template a finding. Total over what exists rather than over what was named, so a kind that renders or stops rendering costs this stage no line.
- **The base an Id is typed by is read from `app.json`, never from the database.** `platformid` is declared there precisely for the case where the database does not yet hold the type, and a check that reads nothing cannot ask which it is — so validate takes the declaration and refuses without it. That refusal is the TOOL failing to run and not a finding: it says nothing about the endpoint, and it is the only throw the validator lets out.
- **`--database` is one more stage, not another mode, and is deferred.** Every action of the endpoint loaded with `Id=0` through the ordinary path — not a DDL diff and not a parse, because it subsumes both: a stale deploy fails the select, a bad expression fails the execution. `edit` with `Id=0` is the new-record branch, which is where defaults, `initials`, `fixed`, an empty autonum and a state's `Initial` all land at once. It does not reach save or post: both write data, and a check does not.

## MCP: the entities the model sees

`mcp.json` lists the endpoints open to the model; everything else is derived from what the endpoint already declares, and an optional `mcp` key of its `metadata.json` corrects what derives wrong. One provider (`MetadataMcpToolProvider`, `Mcp/`) gives three tools: `domain_info`, `entity_info`, `catalog_find`. The platform side — interface, handlers, roles, clients — is [A2v10.Mcp/CLAUDE.md](../../A2v10.Mcp/CLAUDE.md). Decided 2026-10-01, refined and built 2026-10-02; run on the stand through the provider (no OAuth).

- **`mcp.json` in the application root: `endpoints`, a list of paths.** It is the inclusion and the cheap index — no folder walk. Its schema `mcp-json-schema.json` sits with the others in `A2v10.App.Assets2026/Application/@schemas`.
- **The instructions are `mcp-instructions.txt` beside it** (`MetadataMcpInstructions`, 2026-10-02), not a key of `mcp.json`: plain text, and JSON has no multi-line literal. One per application, read per request without a cache. The contract and the reasons: A2v10.Mcp/CLAUDE.md, "Descriptions".
- **The rest is derived, never repeated.**
  - Name: the second segment of the path (`agent`); two equal names are refused. Folder names are the domain words the author already chose — the model maps "контрагент" to `agent` itself. `catalog`/`document` from the first segment, through the `app.json` aliases.
  - Roles: the root `roles` of the folder's `model.json`, the `ModelJson.CheckRoles` predicate; none — open to all, as in the UI. A role means one thing on both sides.
  - Search (catalogs only): the presentation → `contains`; a string field declared `unique` → `exact`. A code is found exactly only when declared `unique`; a code that is not unique is a bad exact key anyway. Not the autonum: a number is the platform's, the model never searches by it.
- **Rejected sources.** `menu.json`: navigation of a screen, another reader, and a menu may live in the database (`MENU_PROC`). The `description` of `metadata.json`: notes for the developing model, "nothing reads it" — another reader. A list of entities with path, description, roles and search in `mcp.json`: the endpoint repeated far from itself, growing with the application.
- **`mcp` in `metadata.json` is optional and holds only what derives wrong.** `description` — when the folder's name is not enough. `searchBy` (catalog only) — field → `exact` | `contains`: a map, because a field has exactly one mode; `contains` and not `like`, which does not say where `%` stands. Written, it REPLACES the derived set whole — "whole or nothing", as forms: a partial override asks at every field "instead or on top". Listed in the schema's `properties` (`additionalProperties: false`); `searchBy` has `minProperties: 1`, so a written set is never empty.
  - **Read by the index, not by the endpoint load** (`McpIndex`, parsed for that key alone; `McpDeclarationMetadata`, not a member of `DeclarationMetadata`). The key is per address by construction — the index reads the address's own file, so nothing can layer it from `storage` (`waybillout` and `waybillin` over one `/document` are two entities).
- **Lazy.** The index (`mcp.json`, the kinds, the roles, the `mcp` keys) is loaded at the first `tools/list` — the schemas enumerate the entities — and cached with the metadata: `ClearAll` drops it, and the watcher drops it alone on an edit of `mcp.json` or a `model.json`. An endpoint is loaded at the first tool call that needs it — `domain_info` loads every listed one the user reaches (its words are spelled from the shape), `entity_info`/`catalog_find` the one asked. Not lazier than the platform anyway: the deploy check loads every endpoint of the application on the first request. Two checks, split by what each can see:
  - **The index load:** a path of two segments, of kind catalog or document, with a `metadata.json` in its folder; two equal names. Refused naming the path — and the refusal fails the whole `tools/list`, the host's bug made loud, as a name collision. Here and not in `a2 meta validate`, which takes one endpoint and never the application (Tools/A2v10.Cli/CLAUDE.md).
  - **`a2 meta validate <endpoint>`, an `mcp` stage** (not built): a listed endpoint resolves to a data endpoint; every `searchBy` field exists and is a string, and `searchBy` is not written on a document; `mcp` written on an endpoint absent from the list is refused — nothing would ever read it. Without the run, a wrong `searchBy` field surfaces at the first `catalog_find`.
- **Per user, in the provider.** The tools exist for everyone (`Roles = null`); the entities the user's roles reach are the enums of their schemas. None reached — no tools; no catalog reached — no `catalog_find`.
- **One projection of a record, three readers** (`McpProjection`). Named as in the shape; `entity_info` describes it, `catalog_find` returns rows in it, `entity_crud` will accept it. Built first, so that no single tool's SQL decides what a record is for the model.
  - **The fields: every column but `TableColumn.IsMcpColumn`'s exclusions.** `rv` (binary, says nothing), `Void` (a voided record is never shown, so always 0), `Master` and `RowKind` of a collection row (the same value in every row: the header's id, the composed collection's kind), the stamps (2026-10-02: a bare user id and a time, never sent, read by no step of any flow — "posted or not" is `Done`, "entered yesterday" is a filter of a future `entity_query`, not a field; four of eleven fields of a catalog, six of a document, in every row `catalog_find` returns). Everything else is shown, since the model reads it: `Done`, `IsSystem`, `Operation`, `basedOn`, the number.
  - **A reference as `{Id, Name}`**, `Name` the target's presentation. **Record data is named as in the shape, the reference object included; the tool's own vocabulary is camelCase** (`rows`, `totalCount`, `type`, `values: [{id, name}]`). It was `{id, name}` — the Web policy camel-cased an anonymous object — beside `Id`, `Name` of the record itself; a blind run flagged it: the model writes back what it reads (2026-10-02). **An enum or a state as its code** — the value travels as its own code, as everywhere in the platform (`IsSetRef`); what a code means is in `entity_info`.
  - **Row kinds are their composed collections** (`StockRows`, `ServiceRows`), each with its own rules (`RowSetDeclaration` — the kind's over the collection's), so the model sets no `Kind`. A flat collection would have to say "required when Kind = Stock": one concept under two names. On write the platform sets `Kind` from the collection's name — `entity_crud`'s business.
  - **Not the form.** A form is a screen, and a declared one may hide a field for layout; the model need not know how a record is shown. The price over a shared `/document`: `waybillout` shows `StoreTo` of the move — optional, left empty; what matters at the address is its `required`.
    - **Open (2026-10-02), before document create:** every run stumbled on this price — a sighted one and two blind ones asked why a receipt has `StoreFrom`, a move `Agent`, `Contract` and `ServiceRows`. Seen, not yet weighed against "not the form".
- **`domain_info`** — no parameters: the listed endpoints the user's roles reach — name, `catalog`/`document`, `title`, `operations`, `description` when written.
  - **`title` and `operations` are the words the user calls the thing by — the screens' own** (2026-10-02). A document: its operation key `@[Operation.<name>]`, the page header ("Прибуткова накладна"); its listed operations by code, `@[Operation.<document>.<operation>]`, the create menu ("Безоплатне отримання"). A catalog: `@[<Model>]`, the title of its dialog ("Контрагент"). One spelling, `MetadataExtensions.OperationLabel`/`RecordLabel`, read by the XAML builders and by `domain_info`, so the screen and the model cannot be told two different words. Localized in the user's locale; a key without a translation comes back as itself and is KEPT (`"title": "@Operation.order"` on the stand), as the screen shows it — the rendered key is the one place a missing translation is seen, and dropping it here would hide it. Not invented, not declared again: no `mcp.title` — a missing word is a missing translation, fixed where the screen gets it too.
  - **`instructions` say what the application is and send the model here**; the glossary is not repeated there (the stand's first instructions were exactly that repetition).
  - **Open (2026-10-02), before document create: an operation has no code here.** `operations` are titles only, `Operation` is `readOnly` in `entity_info`, and its `default` is the code for an implicit operation (`waybillmove`) and nothing for a listed one (`receipt`, chosen by `?Op=`). Two blind runs found it independently: the model cannot say which operation it creates. Likely `{ name, title }`, `name` what `?Op=` takes — decided with the create.
  - Nothing about search here: every catalog is searchable (a catalog always has a presentation, `TableMetadata.SetDefaults` refuses one without); by which fields is `entity_info`'s `search`. Its description says: call once at the start of a task. The glossary lives here, not in `instructions`: it depends on roles.
- **`entity_info(entity)`** — the projection: `type` (the declared column type, camelCase), `required`, `computed`, `readOnly`, `default`, `catalog`/`unavailable`, `values`, `search`; for a document, `collections` with their fields. An optional key is absent, never null or false.
  - **`search` on a catalog's field — `exact` | `contains`: what `catalog_find` matches it by** (2026-10-02; `McpProjection.SearchSet`, read by both). The description of `catalog_find` said "by its codes exactly" for every catalog, and the stand has no codes at all; a blind run tried to search by code. Now the description points here, and the set is per catalog.
  - **A reference to a catalog names it under the key `catalog`** (was `target`, 2026-10-02): the key says the kind and the next step at once — the value is `catalog_find`'s parameter as it stands. A bare `target` left the model to look the kind up in `domain_info`, and `entity_info` is read on its own. Matched by the exact path among the listed catalogs the user reaches: a second address with `fixed` (`catalog/customer`) is not its table's other address — finding a supplier where only a customer may stand is the error it prevents.
  - Otherwise — not listed, hidden by roles, not a data endpoint (a folder, an account), **a document** — `unavailable`, with no name: the model learns before create that it cannot fill the field, and a hidden entity is not named. A document because nothing finds its id yet; with its search it gets a key of its own (`document`) and a tool of its own.
  - No formulas: `computed` says the platform computes it (the model sends qty and price, never the sum); `default` says what fills an empty field — a literal, `today`, `from Item.Unit` for an `inherit`; an initial chosen by the url (`?Op=`, the folder) has none.
  - `readOnly` — written by the platform or fixed by the address: `Id`, `Done`, `IsSystem`, `Operation`, a state, `RowNo`, the number when the endpoint declares a numbering (typed by hand otherwise), `basedOn` in the header (in a row it is picked), a `fixed` field. The model reads it and never sends it. The number carries no `default`: the word "autonum" says nothing to the model.
  - An enum carries its values inline, `[{id, name}]` — the living ones, without the filter's `All` row (key `''`); read from the file, no database. Repeated in every field that has it: a few rows, cheaper than an entity of its own. A state carries its values too, for reading — and is `readOnly`: once transitions exist, offering every value is the picker's lie.
  - Open: a value's `name` may be a resource key (`@…`) — shown as is. Localized by the user's locale when the first real key appears.
- **`catalog_find`** (was `entity_find`) — candidates `[{text, catalog}]`, batched. **Catalogs only:** the references the model fills itself are catalogs; a set is a value of `entity_info`; a basis is set by birth. A document is not found by text — its search is other logic, not built.
  - `catalog` is required: searching every catalog is 5 rows × the card × every catalog of tokens. The enum is the listed catalogs the user reaches.
  - `exact` is `=`; `contains` is `like` over the text with `%`, `_`, `[` escaped — a substring, not a pattern the model writes.
  - A trimmed text under 3 characters is matched by `exact` fields only. What it prevents: `Name like N'%A%'`. The description states the rule.
  - **A candidate that cannot be searched answers alone — `{text, catalog, error}`** — too short with no `exact` field left, or an unknown catalog; the others in the batch are answered (2026-10-02). It was `isError` for the whole call, "a batch half answered is a batch to resend anyway" — but resent is only the failed candidate, and a blind run called the all-or-nothing a defect of a batched tool. A malformed candidate (no `text`, no `catalog`) still fails the call: that is a wrong call, not a hard search.
  - Per candidate: up to 5 records in the projection (the header; a catalog's collections are not read), `by` (the field that matched), `totalCount` (exact, `count(*) over()`), `truncated` (more than 5). Order: `exact` hits, then by presentation. Five: past five the fields do not tell them apart — narrow instead.
  - The same rows a picker of the address offers: `Void = 0` and the address's `fixed` (`SqlBuilder.FixedPredicate`, made static so both read one predicate). No owners and no `inherit`: the model has no record they would come from.
  - The SQL lives in `Mcp/`, not in `SqlBuilder`: find is not a command any screen calls. Through `LoadModelSqlAsync`, as the fetch: the platform's connection pipe, not a raw one.
  - Not built: a `words` mode (all words, any order) — the weak step of the PDF flow, items under the supplier's names. Waits for a stand run that counts the retries.

## Test environment: a service of the test host

`Testing/TestEnvironment` — the database a run owns and the scenarios over it. Registered by `UseTestEnvironment()` (it brings `UseEndpointDataServices`), which only a test harness calls; the harness gives paths and the user, nothing else. Decided and built 2026-09-24.

- **The test database is protected by its NAME, and the name has one owner.** The harness points the host's `Default` at `TestConnectionString(app's)`, so inside the host the test database IS `Default` and nothing else can tell it from the application's. `TestConnectionString` appends `_Test`, `CreateTestDatabaseAsync` refuses a name without it — one class writes and reads the suffix, so a run against the application's data is not expressible.
- **Recreated at the start, never dropped.** After a failure the state is still there to open the application on. There is no `Drop`: `Create` removes the old one first, and nothing else would call it.
- **`full.sql` runs through the deploy's executor**, `SqlDbGenerator.DeployDatabaseAsync` — the road `a2 meta deploy --full` takes: one batch splitter, a failure reported as lines of the file. The metadata is deployed after it by the caller: `deploydatabase.sql` inside `full.sql` is the one on disk and may be older.
- **The host is built before the database exists.** It needs none at start (checked by the stand run); so the database is created by a service of the host rather than in a configuration callback.
- **`ScenarioRunner` and `Door` are internal.** The scenario format is the contract (the skill's `tests.md`); the runner is how this layer reads it. Every step opens its own scope, as a request does.
- **The runner knows no platform convention; `EndpointDataService` does** (`DataAt`: index, load, create, save, post, unpost; one service for API, CLI and tests). A new record is `edit/new`, never `edit/0`: the server takes both as new, but the client treats `/0` as new only in a dialog, and a page opened at `/0` gets no id after save. The record is found by `!MainObject`, which the edit procedure marks.
- **The user and the module paths are the host's.** The harness registers `DefaultAdminUser` (`UseEndpointDataServices` does not: an API brings its own authentication) and gives absolute module paths, as `TestHost` and the CLI do; nothing resolves against the current directory. 2026-09-24.
