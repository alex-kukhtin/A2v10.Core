# Blobs — files and images: `a2blob`, the `blobs` section, the `_blob` route

> Decisions, why, and what was refused. Not a design thread. Names marked *working* may change. Decided 2026-10-12/13.
>
> Built (2026-10-13, live sample `catalog/agentblob` on MetaAppStand): `a2v10_blobs_simple.sql` (tables, `Blob.Insert`, `Blob.Load`; bundled into `a2v10_platform_simple.sql`), `ModelJson.Blobs` (`ModelJsonBlobNew`), `IBlobService` / `BlobService`, `BlobController` (upload + read), the Save token check (probed on the stand: a foreign `Logo.Id` with the old token fails both the read and the Save), `BlobImage` + client `a2-blob-image`, the first-bytes type check; attachments — `requireBase`, the upload with its link (`UploadLinkAsync`, `Blob.Insert` with `@Base`/`@LinkId`), the base's roles, `BlobPreview` + `a2-blob-preview`, `$uploadBlob` (live sample `attachment/` opened from the agent's dialog); `requireBase` on every call (`DataService.LoadViewAsync` and `InvokeAsync`, one check `BaseAccess`). Not yet: compression, tools (decided, deferred — see Tools).
>
> Pinned by `Tests/TestServices/BlobServiceTests` (category `Blobs`): the type of an upload (bytes win, a claimed inline type without its bytes refused, accept by the real type, maxSize, the door key, the endpoint's roles, nothing written on a refusal), the read (the issued token reads, a wrong one is refused before Storage), the Save check (empty passes, a foreign id / no token / a bare scalar refused, names ignore case) and its wiring in `DataService.SaveAsync`; attachments (the link written with its owner and base, a field door links nothing, an attachment door needs base and owner, a base without `model.json` and a base of foreign roles refused) and `requireBase` through `DataService` (a load without base, a load under a foreign base, a command checked by the `Base` it posts). Not tested: `BlobController` — three lines of headers in one place; the one decision there that could rot quietly is `IsInlineMime` (someone adding SVG), a table test on it if it is ever wanted.

## Storage: bytes never in the application

- **Bytes are never in application tables, procedures or models — hard.** The application sees `Id` and `Token` only. A skill ban at every point where storage is chosen.
- **Where bytes live is a deployment choice, not the developer's.** Provider from host config (`BlobStorage:Provider`, `BlobStorage:Path` for FileSystem); several providers per host (`BlobStorageFactory`); dev and prod differ by config only. `model.json` and application code do not depend on the provider.
- **"In the database" is one more provider (`SqlServer`)**, bytes in its own `a2blob` table, never in application tables. Why: one database backup is everything; a farm without a shared folder. Price: garbage is never collected, so the database grows with every backup — on SQL Server Express the 10 GB limit is real. One line in the provider docs, no check.
- **Default for new projects: FileSystem** — works in dev and on a stand with no infrastructure.
- **`a2blob` lives in the model's database** (the tenant segment, if several), not in the `a2security` database: application FKs and joins look at `Blobs`, and they do not cross databases.
- **An endpoint with its own `source` cannot have `blobs` — loud error** (`a2 meta validate`, `resolve-*`). `_blob/<blobId>` carries no database, so a blob in a named source would upload and never read. Refused: the source inside the token (`<source>.<hash>`) and reading through the door address — not worth it now; the token variant is the minimal path if it is ever wanted.
- **Old storage is deprecated, not migrated:** `Image` + `Model.Property.Load/Update`, `files` with `type` = `sql` / `azureBlob` / `blobStorage` / `clr`, the `_file` route. Silence in skill and docs; `_blob` stands beside it, no compatibility. `files` + `parse` (importing rows from a file) stays — a different class of task.

## Tables

- **`a2blob.Blobs`: `Id, Name, Mime, BlobName, ThumbName, AccessToken, UserId, UtcDateCreated`.** Immutable; replacement = a new `Id`. The application never writes it; it reads it in its own `Load` (join for `Name`, `Mime`, token). `UserId` + `UtcDateCreated` are audit. Refused: an origin door column — nothing reads it since the Save check moved to the token, and where a blob is used is told by its reference.
- **Ownership is decided by the reference, not the blob.** `Blobs` has no back link.
- **`a2blob.BlobLinks(Id, Base, LinkId, Blob)` — the attachments link table is the platform's, one per database**; `LinkId` is `platformid` — an owner's key is the application's type ([platformid.md](platformid.md)); so models do not invent their own. Only the table is the platform's: there are no platform procedures over it — `Index`, `Delete` and the rest are the application's and read/write `BlobLinks` directly. Own columns (Memo, category): `alter table a2blob.BlobLinks add …` in the application's `schema.sql`, guarded by column. Refused: platform `Memo`/`Category` — an application adds what it needs; a category is either a reference to its own catalog (no FK from a platform table) or a string nobody owns.
- **`BlobLinks` has its own `Id`** — as every A2v10 row (`[Id!!Id]`, TVP merge, the Metadata layer). Refused: a natural key `(Base, LinkId, Blob)`, which made "delete only by link id" impossible by construction but put the table outside the machinery. Price: that rule is the author's again. `UNQ_BlobLinks (Base, LinkId, Blob)` forbids a duplicate and is the index for the owner's list.
- **Named `BlobLinks`, not `Links`:** `Links` is taken in the Metadata layer, and application procedures read it next to their own tables, without the schema.
- **`simple` is single-tenant**: no `TenantId` in either table.

## References and count

- **Count is never declared — it follows from where the reference lives.** An entity column (`Agent.Photo`, `RefId`) — one blob, written by Save; a separate endpoint with its own `Index` over `BlobLinks` — many.
- **Every reference column has an FK to `a2blob.Blobs`** (`keys.sql`). Integrity, and the only thing that keeps a future collector possible.

## Access

- **Read = token.** Only the application's `Load`/`Index` issues it (`[Token!!Token]`, hashed by A2v10.Data through `ITokenProvider`); `_blob/<blobId>?token=` checks nothing else.
- **Token = hash(`AccessToken`, user) — no session** (`WebTokenProvider`, all routes: `_blob`, `_file`, `_image`). `Session.Id` died with 20 idle minutes or a restart, while a token issued by `Load` must survive an open form until Save; the user in the hash keeps it unforwardable, and a stable URL lets the browser cache live its 30 days. Revoked rights: the user can re-read a blob already seen — immutable, the bytes were already theirs. Price: an old `Image` overwritten under the same `AccessToken` may be served from the browser cache until it expires. Refused: a parameter on `ITokenProvider` — its main caller, `DataModelReader`, sees only a `Guid` and cannot fill it. The token was the session's only writer, so the platform has no session at all now (`AddSession`, `UseSession`, `AddDistributedMemoryCache` removed).
- **A reference written through Save carries its token — checked by the platform before `Update`.** Without it, Save with a guessed `Photo.Id` (ids are sequential) makes the next `Load` issue a token for any blob in the database — another owner's attachment, another tenant's. "Load already showed it" holds only while the client does not write the column.
- **Where:** `DataService.SaveAsync`, before every branch (metadata, handler, classic), when `IModelView.BlobKeys` is not empty; the check itself is `IBlobService.CheckReferencesAsync`, beside issuing the token — one rule. `IBlobService` comes as an optional constructor parameter (as `IAppClrManager`): a host without blobs need not register it; doors declared and no service — loud. Contract: `IModelView.BlobKeys` is a new member of an existing interface (implemented only by `ModelJsonView`). Refused: casting the view to `ModelJsonBase` and resolving `BlobService` as a class — the same check without the contract, ugly.
- **The token field is named `Token`** in the blob type (`[Token!!Token]` in `Load`), as in the upload response: the posted data do not carry the meta name. Another name — Save fails loudly. A bare scalar instead of the object (`Logo: 1234`) is a reference without a token and fails too.
- **Which fields: model + door key.** Door `blobs.<Key>` of an endpoint with `"model": "Agent"` is field `Agent.<Key>`; compared IgnoreCase, written PascalCase (one name in `model.json`, SQL and XAML; the schema does not enforce it). Per door: empty — skip (clearing is always allowed; an empty `RefId` arrives as an object with `Id` 0, not `null`, and the platform writes `null` to the column); otherwise `{ Id, Token }` is checked against `Blobs.AccessToken`; missing or wrong → loud error, `Update` is not called. The client always posts the whole model, so the token is there. An honest reference always has a token — from `Load` (unchanged) or the upload response (new); the old value need not be known; copying someone's photo through the client passes — whoever saw it has the token. Refused: recognising blob fields by the posted shape — the attacker drops `Token`; a `bind` key on the door — model + key already name the field.
- **Only a root field.** `Agent.Contact.Photo` or an image in a row (`Document.Rows[].Photo`) cannot be addressed, and unchecked they are the same leak — forbidden; images in rows are not built.
- **Accepted: another endpoint writing the same column** (import, bulk edit) bypasses the check. Closing it means a recursive rights check; the author's responsibility, as for any column.
- **Attachments are addressed by `base` = an endpoint address** in the URL (`/attachment/index?base=/document`) — the same word and meaning as `base` in reports and `Base` in the old `Image`. `base` is an ownership area the author chooses: `/document` — shared by all document kinds; `/document/invoice` — its own. The platform reads `model.json` at `base`, checks its roles (and those of `attachment/`) before any procedure, passes `@Base` as is.
- **`base` must point at a `model.json`** — roles come from there; it may hold roles only. None → loud failure, or the request would pass unchecked.
- **Price of `base`:** `base=/document` = "every role of `/document` sees document attachments" — coarser than invoice roles. Finer: a lower `base` or row checks in procedures. Renaming the folder → one `update` over `BlobLinks`.
- **Protection lives in procedures, not roles.** `base` roles stop only someone with no access to any owner: pass your own catalog's `base` and a foreign link `Id` — roles pass. So every procedure working under `base` filters `@Base` + owner id; deletion is by owner + id, never by the link id alone. A foreign `base` then finds nothing; a call without `base` (`@Base` = null) too.
- **`requireBase`** (*working*, `ModelJson.RequireBase`, `IModelBase.RequireBase` — a new member of an existing interface, implemented only by `ModelJsonBase`): one declaration for "this endpoint lives under `base`" — every call carries it (loud without it: against a developer's mistake, not an attacker), its roles are checked, and an upload into its doors links the file to the owner.
- **Where the base is checked: the two doors every call goes through.** `DataService.LoadViewAsync` (load, save, remove, expand) reads `Base` from the query — a view posts nothing that could replace it; `InvokeAsync` reads it from the final parameters, after the posted data joined them — a command may post its `Base` (the attachment delete does), and the one checked is the one the procedure gets. Without this, `/attachment/index/<id>?base=<anything>` listed another area's attachments — and their tokens — to a user with the roles of `attachment/` alone: the procedure filters by base and owner but cannot know who may look at an area. One check (`BaseAccess.CheckAsync`) for `DataService` and the upload: `model.json` at the base or loud, its root roles by `ModelJsonBase.CheckRoles`. `DataService` takes `IModelJsonPartProvider` for it — the roles of a root are not reachable through `IModelJsonReader`.
- **The platform inserts the link; no hook.** `Base` from the address, `LinkId` = the owner, `Blob` = the new id — nothing for an application to decide, and a hook would be one procedure every application writes the same way. Atomic: `a2blob.[Blob.Insert]` takes `@Base`/`@LinkId` and writes the blob and its link in one transaction. Own columns of a link — a second call. Price: the upload checks the base's roles, not the owner's row — a user of `/document` may attach a file to document 42 they cannot see, if they know its id; reading others' attachments stays impossible (the list is the application's `Index`). If ever needed: an optional veto procedure after the insert.
- **Row level** ("this user does not see document 42") is the application's procedures (`@Id`, `@UserId`), as everywhere in A2v10.

## Upload and read

- **`blobs.<Key>` in `model.json`: `accept` (MIME, `type/*` allowed), `maxSize` (KB) — checked by the server.** The door takes the roles of its endpoint (`ModelJsonBlobNew : ModelJsonBase`), checked by the same `DataService.CheckAccess` as everything else.
- **The logic lives in `A2v10.Services` behind `IBlobService`, the controller is thin** — as `FileController` → `IDataService`. `Platform.Web` sees `model.json` only through `A2v10.Infrastructure`, so a new interface there was unavoidable: `IBlobService` (new, nothing existing changed). Refused: a method on `IModelJsonReader` — changes an existing interface and fattens the controller.
- **The service issues and checks the token**, through `ITokenProvider` — one place for the rule. A wrong token reads nothing: it is checked before Storage.
- **Upload: `POST _blob/<endpoint>/<Key>[?base=…&owner=…]`**, the file in form field `file`. The path is always endpoint + key; the owner rides in the query — `<endpoint>/<Key>/<ownerId>` was ambiguous (`catalog/agentblob/Logo` and `attachment/Upload/1000` are both three segments). The platform generates `BlobName` (`{yyyyMMdd}/{guid}_{name}`; a tenant prefix when multi-tenant), writes Storage, inserts `Blobs` (`a2blob.[Blob.Insert]`).
  - **A field door** (no `base`): the client gets a flat `{ Id, Token, Name, Mime }`. Uploading alone binds nothing: a photo is bound by Save. Into an endpoint with `requireBase` — refused.
  - **An attachment** (`?base=` present; `UploadLinkAsync`): the endpoint must declare `requireBase`, `owner` is required, the base must have a `model.json` and its roles must admit the user (`ModelJsonBase.CheckRoles`, the one predicate, made static for a root). The client gets the row: `{ Id: <link>, Blob: { Id, Token, Name, Mime } }`. The owner travels as text; the `platformid` parameter converts it to `bigint` or `uniqueidentifier`, and a malformed one fails there, loudly.
- **`$uploadBlob(url, accept)` is a controller method that returns the result, not a `BindCmd`.** What follows an upload — append the row, reload, select it — is the application's: only it knows the shape of its row. A command would have to choose for it. Refused: `{BindCmd UploadBlob}` then `$reload()` (a choice made for every application) or `$append` (a naming contract between the platform's response and the application's `Index`). The method takes the owner and the base from the dialog's own address (`urltools.parseUrlAndQuery($baseUrl, $baseQuery)` — `$baseUrl` carries its query), so the markup passes nothing.
- **No provider — loud:** no `BlobStorage:Provider`, an unregistered name, or no `AddBlobStorages` each fail the request. `IBlobStorageProvider` is resolved on use: it exists only in an application that registered storages. `SqlServer` refuses loudly until it is built.
- **The type of a blob: the bytes for the inline types, the name for the rest, the client's `Content-Type` never.** PNG, JPEG, GIF, WebP, PDF are recognized by the first bytes (`BlobSignature`) and win over the name. A name claiming one of them without its bytes (`a.png` holding HTML) is refused. Anything else keeps the type by the name — `FileExtensionContentTypeProvider` in the controller, unknown → `application/octet-stream`; a browser derives its `File.type` from the extension too, but by its own table per browser and OS (an empty type for `.docx` without Office), so one server table makes `accept` behave the same for everyone. An inline type can come only from the bytes — by the rule, not by a separate check. SVG keeps `image/svg+xml` by the name: never inline, but `<img>` draws it (`Content-Disposition` does not apply there) and runs no script. Office files are not sniffed: always an attachment, and docx/xlsx share one ZIP signature. The stream is seekable (`IFormFile`'s always is); any other fails loudly on `Length`/`Position`.
- **Read: `GET _blob/<blobId>?token=[&thumb]`** — `a2blob.[Blob.Load]`, no application procedures. Inline only raster images and PDF, by the type stored at upload (from the bytes), never the client's MIME; everything else `attachment`; `nosniff`. `&thumb` without a thumbnail → the original; that branch exists only here.
- **Cached on success only:** `WebBinaryActionResult.EnableCache()` (`private`, 30 days) — blob immutable, token stable. Refused: `[ResponseCache]` — a filter sets the header before the action, so a status-255 error was cached for 30 days too. `_file` and `_image` moved the same way; `_static_image` keeps the attribute (its error is `WriteImageException`, whose `no-store` replaces it).
- **No CSP `sandbox`.** A raster runs no script; JS in a PDF runs in the viewer's own isolation; `sandbox` risks breaking PDF in `<object>`, which is how `FilePreview`/`PdfViewer` show it. Insurance that does not pay.
- **The same rule hardened the old routes:** `_file` and `_image` now send `nosniff` and `attachment` for anything but raster and PDF — they stored the client's MIME and served it inline, so an uploaded `.html` ran in our origin. One predicate, `BaseController.IsInlineMime`.
- **No explicit delete.** Removing a reference (new `Photo.Id`, deleted link row) leaves an orphan.
- **No garbage collection — accepted.** Garbage (replaced photo, upload without Save, removed link) stays in Storage: it is cheap, and every collector rule — threshold against session life, row/file order, files without a row — is complexity that does not pay. If ever wanted: a nightly `A2v10.Scheduling` task over the same model, on the condition of an FK on every reference column (`sys.foreign_key_columns` is its only source of "alive / orphan"). Its rules are written when it is built.
- **A hard `Delete` of an attachment owner cleans its links — hygiene** (`delete from a2blob.BlobLinks where Base = … and LinkId = @Id`). `LinkId` is generic with no FK to the owner, so a link outlives its owner and holds the blob. `Void` keeps links — the record can be restored.

## Images: compressed in the browser

- **The client compresses; the server decodes nothing — it only checks.** Server-side processing does not pay.
- **The numbers live on the control, not the door** (*working* `MaxDimension="1600" Quality="80" Thumbnail="200"` on `BlobImage`). They are a client rule only, and the render knows nothing of the endpoint, so it cannot read them from `model.json`. Refused: an `image` key on the door — the server never applies `maxDimension`, and the view engine would have to resolve the door.
- **Only `BlobImage` compresses.** The attachments upload does not.
- **Client:** `createImageBitmap(file, { imageOrientation: 'from-image' })` → `canvas` (down to `maxDimension`) → `toBlob` JPEG at `quality` (PNG if transparent). Always re-encode, even with nothing to shrink: metadata (GPS included) is dropped by the canvas re-encode, not by the resize. The thumbnail goes the same way, as a second file in the same request.
- **Server:** byte size (`maxSize`), the real type from the first bytes, width/height from the header (PNG `IHDR`, JPEG `SOF`). Two limits: `maxDimension` is the client's target and the server does not apply it (it would reject non-browser uploads); the server rejects only above the platform anti-bomb limit (around 10 000 px, the platform's, not the door's). No decoding — no decompression bomb. **The thumbnail passes the same checks** (type, bytes, the platform dimension limit — the server does not know the control's `Thumbnail`): it is served inline, there can be no unchecked channel.
- **Thumbnail = `Blobs.ThumbName`** in the same row: no id, owner or token of its own. May be absent (API, import) → read returns the original.
- **Price:** a malicious client skips compression but not the byte limit or the dimension limit; the worst is its own GPS in its own file. Non-browser uploads get no processing: the original within `maxSize`, no thumbnail.
- **Refused:** WebP output — reports and export may not accept it. Server processing at all. `System.Drawing.Common` — Windows only since .NET 6. SkiaSharp — native assets per RID, musl, `fontconfig`, exact version match (QuestPDF left it for its own Skia build). ImageSharp — license is fine (Apache 2.0 transitively), refused with server processing. Magick.NET, NetVips — heavy native. `StbImageSharp` — transpiled C on `unsafe`, the original not meant for untrusted files. Rendering through QuestPDF — a detour.
- **`imageCompress` of the old `files` never worked in Core** (schema and docs only, `ModelJsonBlob` lacks it) — nothing is lost.

## Controls

- **The render knows nothing of the endpoint.** Whatever a control needs is in its markup, as `Image.Base` and `FileImage.Url`.
- **`BlobImage`** (*working*): `UIElementBase` with `Url`, `Value`, `Width`, `Height` — the `FileImage` set. `Url` = the endpoint (`/catalog/agentblob`); the door key = the bound property, so the client posts to `_blob/<Url>/<prop>`. `Value` renders as `:item` + `prop` (as `Image.Source`), not `:value`: the control writes back. Refused: `Control` as the base — `Label`, `Required` and the rest are not needed; the full door address in `Url` — the field name twice, free to diverge. Shows, picks a file → uploads → `Id`, `Token`, `Name`, `Mime` into the referenced object (model dirty, as any field); clear → `$empty()`. Works on a new record (bound by Save); Cancel changes nothing. URLs are never built by hand.
- **`BlobPreview`** (*working*) — canonical preview/download for `_blob`: `UIElementBase` with `Value`, `Width`, `Height`, `Value` as `:value` (shown, not written). An image (svg included — `<img>` runs no script), a PDF in `<object>`, anything else its name as a link (served as `attachment`, so the click downloads). **No `Url`:** a blob is read by its own id and token, and the token is the right — `Url` is for a control that writes (`BlobImage` needs the door). Donor: `FilePreview`, which has `Url` because `_file` reads through the endpoint's `model.json`; two controls for one task confuse a model, so the new one gets its own name and `FilePreview` stays silent in skill and docs.
- **The selected row is a `Slot`**, not an `If`: `<Slot Scope="{Bind Attachments.$selected}"><BlobPreview Value="{Bind Blob}"/><Slot.Fallback>…</Slot.Fallback></Slot>` — the scope shortens the bindings, nothing under it renders without a selection (`$selected.Blob` on an empty list threw), and the fallback says why the place is empty.

## Tools

Decided 2026-10-13, deferred — not built.

- **`resolve-action` / `resolve-dialog` / `resolve-popup` add `"blobs": [<keys>]` and `"requireBase"`.** One line each: the view already has `BlobKeys` and `RequireBase`. A model writing markup sees which doors the endpoint has and whether it lives under `base`. No `accept`/`maxSize`: not on the view's interface, and markup does not need them.
- **`a2 view validate` checks `BlobImage` — as errors, everything here breaks at run time:** `Value` binds a root field, exactly `<model>.<Key>`; `Url` is given, a `model.json` lies behind it, its `model` is `<model>`, and it has `blobs.<Key>` (IgnoreCase). Needs a walk of the XAML tree, which the command does not have (it only instantiates): reflection over public properties holding a `XamlElement` or a collection of them — one helper in the CLI, the next binding checks reuse it.
- **Refused: warnings on the old storage controls** (`Image`, `FileImage`, `UploadFile`, `FilePreview`). The CLI result has one shape — success or an error; warnings need another, and the CLI's rule is no shape before the feature that needs it. A model writing from the skill never meets the old controls — the skill is silent about them, and that silence is the guard. Warning someone editing an existing application is a different task, built when it arrives.

## Printing

- **Stimulsoft is not supported** — obsolete, will not be used.
- **Rendering does no I/O.** Reading Azure synchronously inside a render hangs the request on a dozen images.

## Open

- **`base` lives in two places:** XAML (`?base=/document`) and the owner's hard `Delete` (`where Base = '/document'`); by `LinkId` alone is impossible (agent 42 vs document 42). Changed XAML, forgot SQL → links are not cleaned. Kept by the author only.
- **Immediate deletion** (personal data): no explicit delete and no collector — a file lives forever. If needed: a targeted explicit delete, not a collector.
- **Printing blobs.** The report image slot (`RenderContext.ResolveImage`) understands `Byte[]` and a file name; a blob reference falls into `_ => null` — the invoice logo disappears silently. Candidates: a cache in the database (the print procedure joins bytes, the engine does not change; `BlobId` is immutable, no invalidation; filled before printing) or prefetch (ids from the model via `IDataMetadata.Token`, parallel async read, a dictionary for the engine). Undecided: how "before printing" knows which ids; original or thumbnail per slot. Cheap either way: a non-empty value in an image slot that is neither `Byte[]` nor a string — loud error.
- **Working names:** `BlobImage` and its `MaxDimension` / `Quality` / `Thumbnail`, `BlobPreview`, `$uploadBlob`, `requireBase`, `ModelJsonBlobNew`; the anti-bomb number.
